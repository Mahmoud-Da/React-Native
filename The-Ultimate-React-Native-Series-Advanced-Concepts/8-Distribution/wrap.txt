*** 2- App Icon ***
# App Icon Configuration in Expo

## 1. Overview

Before creating and distributing the application, we need to prepare some important production assets.

The **first step is configuring a proper app icon**.

Expo makes this relatively simple because we provide **one high-resolution icon**, and Expo can generate the required sizes for different platforms.

---

# 2. App Icon Requirements

The lecture specifies the following requirements for the main icon:

### File format

The icon should be:

-------------------code----------------------
PNG
-------------------code----------------------

### Dimensions

The icon should be exactly:

-------------------code----------------------
1024 × 1024 pixels
-------------------code----------------------

Both dimensions must be identical.

Correct:

-------------------code----------------------
Width:  1024 px
Height: 1024 px
-------------------code----------------------

Incorrect:

-------------------code----------------------
Width:  1024 px
Height: 1000 px
-------------------code----------------------

The icon should be perfectly square.

---

# 3. Don't Add Rounded Corners

The source icon should **not contain rounded corners**.

Use:

-------------------code----------------------
Square image
    ↓
Expo / platform processing
    ↓
Platform-specific icon
-------------------code----------------------

Don't manually create the rounded corners.

The platform handles the appropriate presentation.

---

# 4. Follow Platform Design Guidelines

The icon should follow the design guidelines for both:

* Apple
* Android

This is important because app stores and operating systems have specific recommendations for application icons.

The general principle is:

-------------------code----------------------
1024 × 1024 PNG
        ↓
Platform guidelines
        ↓
Production app icon
-------------------code----------------------

---

# 5. Add the Icon to the Assets Folder

Place the icon inside your project's `assets` directory.

For example:

-------------------code----------------------
project/
├── assets/
│   ├── icon.png
│   └── ...
├── app.json
└── ...
-------------------code----------------------

In the lecture, the provided icon represents the letter **D**, referring to the app "Done."

---

# 6. Configure the Icon in `app.json`

Open:

-------------------code----------------------
app.json
-------------------code----------------------

Expo projects normally contain an `icon` property inside the Expo configuration.

Example:

-------------------code----------------------
{
  "expo": {
    "icon": "./assets/icon.png"
  }
}
-------------------code----------------------

The important part is:

-------------------code----------------------
"icon": "./assets/icon.png"
-------------------code----------------------

This tells Expo where the application's main icon is located.

---

# 7. How Expo Handles the Icon

One of the major advantages of Expo's managed workflow is that you don't have to manually create every icon size.

You provide:

-------------------code----------------------
1024 × 1024 icon
-------------------code----------------------

Expo's build system handles the platform-specific icon generation.

Conceptually:

-------------------code----------------------
                icon.png
             1024 × 1024
                   |
                   v
             Expo Build Service
              /            \
             /              \
          iOS              Android
           |                  |
      Required sizes      Required sizes
-------------------code----------------------

This significantly reduces the amount of native configuration you need to manage.

---

# 8. Expo Managed Workflow vs. Ejected/Bare Projects

### Expo Managed Workflow

You provide one main icon:

-------------------code----------------------
assets/icon.png
-------------------code----------------------

and configure:

-------------------code----------------------
{
  "expo": {
    "icon": "./assets/icon.png"
  }
}
-------------------code----------------------

Expo handles much of the platform-specific work.

### Bare / Ejected Workflow

If you move away from Expo's managed workflow, you generally have to deal with native project configuration yourself.

That can mean configuring:

* iOS icon assets
* Android icon resources
* Different resolutions
* Native project settings

The process isn't impossible, but it requires more manual work.

---

# 9. Why Expo Makes This Easier

The main advantage is **less native configuration**.

Without Expo:

-------------------code----------------------
Create icon sizes
       ↓
Configure iOS
       ↓
Configure Android
       ↓
Maintain native assets
-------------------code----------------------

With Expo:

-------------------code----------------------
Create one 1024 × 1024 PNG
       ↓
Configure app.json
       ↓
Expo handles the rest
-------------------code----------------------

This is one of the conveniences of the managed workflow.

---

# 10. Best Practices

### Icon checklist

Before building your application:

* [ ] PNG format
* [ ] Exactly 1024 × 1024 pixels
* [ ] Width = height
* [ ] No manually added rounded corners
* [ ] High-quality artwork
* [ ] Follow Apple design guidelines
* [ ] Follow Android design guidelines
* [ ] Place the icon in `assets/`

Don't resize the image to different dimensions yourself unless you have a specific reason. The production build system can generate the required platform-specific versions.

*** 4- Optimizing JavaScript Bundle ***
# Optimizing Production Assets in an Expo App

## 1. Why Do We Need to Optimize Assets?

When we build the app for production, assets such as images are bundled into the application.

For example:

-------------------code----------------------
assets/
├── logo.png
├── couch.jpg
├── chair.jpg
└── jacket.jpg
-------------------code----------------------

These files can increase the final application size.

The goal is:

> Keep only the assets that are absolutely necessary when the app starts.

Anything that isn't immediately required should preferably be downloaded later from the internet/server.

---

## 2. Remove Unnecessary Assets

Earlier in the course, some images were used as temporary data before connecting the application to the backend.

For example:

-------------------code----------------------
couch.jpg
chair.jpg
jacket.jpg
-------------------code----------------------

Once the application gets its data from the backend, these images are no longer needed.

### Step

Delete unnecessary files:

-------------------code----------------------
assets/
├── logo.png
└── other-essential-assets
-------------------code----------------------

This reduces the size of the production application.

### Important Rule

Before building:

1. Open the `assets` folder.
2. Identify which files are actually required at startup.
3. Delete unused or obsolete files.
4. Move remotely available content to the server/CDN when appropriate.

---

# 3. Install `sharp-cli`

After removing unnecessary assets, we should optimize the remaining images.

The lecture uses `sharp-cli`.

Install it globally:

-------------------code----------------------
npm install -g sharp-cli
-------------------code----------------------

### What is `sharp-cli`?

`sharp-cli` is a command-line tool based on the Sharp image-processing library.

It can optimize images and reduce their file size while maintaining good visual quality.

---

# 4. Optimize Expo Assets

After installing `sharp-cli`, run:

-------------------code----------------------
npx expo-optimize
-------------------code----------------------

The optimization process uses Sharp behind the scenes to reduce the size of the images.

For example:

-------------------code----------------------
npx expo-optimize
-------------------code----------------------

The tool processes the assets and reports how much space was saved.

Example:

-------------------code----------------------
Optimizing assets...

logo.png    saved: 20 KB
image1.jpg  saved: 50 KB
image2.jpg  saved: 58 KB

Total saved: 128 KB
-------------------code----------------------

The exact output will depend on your project.

---

# 5. What Happens During Optimization?

Conceptually:

-------------------code----------------------
Original image
      |
      v
   Sharp
      |
      v
Optimized image
      |
      v
Smaller production bundle
-------------------code----------------------

The important point is that the image is compressed/optimized without noticeably reducing its visual quality.

---

# 6. Why Asset Optimization Matters

In the example from the lecture, the optimization saved approximately:

-------------------code----------------------
128 KB
-------------------code----------------------

For a small application, this isn't a huge amount.

However, in a larger application you may have:

* Dozens or hundreds of images
* Large PNG files
* Background images
* Icons
* Fonts
* Other bundled resources

The savings can become significant.

For example:

-------------------code----------------------
100 images × 200 KB
= 20 MB
-------------------code----------------------

Reducing each image by even 30% could save several megabytes.

---

# 7. Best Practices

### 7.1 Don't bundle everything

Only bundle assets that are required immediately.

Bad:

-------------------code----------------------
assets/
├── 100 product images
├── 50 profile images
├── backgrounds
├── unused images
└── temporary test images
-------------------code----------------------

Better:

-------------------code----------------------
assets/
├── app-icon.png
├── splash.png
└── other startup-critical assets
-------------------code----------------------

Download user/content-specific images from your backend when needed.

---

### 7.2 Delete development leftovers

Before production, check for:

-------------------code----------------------
test images
temporary files
unused icons
old screenshots
sample data
unused fonts
-------------------code----------------------

They should not unnecessarily be included in the final application.

---

### 7.3 Optimize images before building

A good production workflow is:

-------------------code----------------------
Remove unused assets
        ↓
Optimize remaining assets
        ↓
Test the application
        ↓
Create production build
-------------------code----------------------

---

### 7.4 Don't sacrifice quality unnecessarily

The objective isn't simply:

> "Make every image as small as possible."

Instead:

> "Use the smallest reasonable file size while maintaining acceptable quality."

---

# 10. Summary

The production asset optimization process is:

1. **Remove unnecessary assets**

   * Delete old/test images such as `couch.jpg`, `chair.jpg`, and `jacket.jpg`.

2. **Keep only essential startup assets**

   * Don't bundle content that can be downloaded from the backend.

3. **Install Sharp CLI**

-------------------code----------------------
npm install -g sharp-cli
-------------------code----------------------

4. **Optimize Expo assets**

-------------------code----------------------

-------------------code----------------------

6. **Build only after the assets are cleaned and optimized.**

### Key idea

> **Smaller bundled assets = smaller application size and potentially faster installation/startup.**

*** 5- Error Reporting ***
# Error Reporting in Production with Bugsnag

## 1. The Problem with `console.log`

During development, we can see errors in the terminal:

-------------------code----------------------
console.log(error);
-------------------code----------------------

For example, in `Cache.js`:

-------------------code----------------------
try {
  // some operation
} catch (error) {
  console.log(error);
}
-------------------code----------------------

This works while developing locally.

However, after publishing the application to the App Store or Google Play, we don't have access to the user's terminal.

Therefore:

-------------------code----------------------
Development
    ↓
console.log()
    ↓
Terminal
-------------------code----------------------

But in production:

-------------------code----------------------
Production App
    ↓
Error
    ↓
Error reporting service
    ↓
Developer dashboard
-------------------code----------------------

We need an **error reporting service**.

---

# 2. Error Reporting Tools

The lecture introduces two popular options:

* Sentry
* Bugsnag

Bugsnag can report both handled and unhandled errors and can provide diagnostic information such as:

* Device information
* OS version
* React Native / Expo versions
* Date and time
* Error stack trace
* Application release
* Error frequency
* User information
* Error timeline

The important concept is that production errors are collected remotely so developers can investigate them.

---

# 3. Install Bugsnag for Expo

The lecture uses Bugsnag's Expo integration.

The CLI installation command is provided by Bugsnag during project setup.

The general process is:

-------------------code----------------------bash
npx @bugsnag/expo-cli init
-------------------code----------------------

During installation, the CLI asks several questions.

### Question 1: Install Bugsnag?

Answer:

-------------------code----------------------
Yes
-------------------code----------------------

### Question 2: Version

Choose the latest version.

### Question 3: Package manager

Choose:

-------------------code----------------------
npm
-------------------code----------------------

or Yarn if that's what your project uses.

### Question 4: API key

Bugsnag provides an API key from the project dashboard.

The API key allows the application to communicate with Bugsnag.

Important:

**Never expose or commit sensitive credentials unnecessarily.** Follow the current Bugsnag/Expo configuration guidance for production secrets.

---

# 4. Automatically Modify `App.js`

The Bugsnag CLI can add the required initialization code automatically.

Conceptually, it adds something similar to:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

Bugsnag.start();
-------------------code----------------------

Now Bugsnag is initialized when the application starts.

However, the lecture makes an important architectural improvement:

> We don't want the rest of the application to communicate directly with Bugsnag.

Instead, we create our own abstraction.

---

# 5. Why Use an Abstraction?

Imagine that today we use:

-------------------code----------------------
Bugsnag
-------------------code----------------------

but later we decide to switch to:

-------------------code----------------------
Sentry
-------------------code----------------------

If every file directly uses Bugsnag:

-------------------code----------------------
Bugsnag.notify(error);
-------------------code----------------------

we would have to modify many files.

Instead:

-------------------code----------------------
Application
     ↓
   Logger
     ↓
  Bugsnag
-------------------code----------------------

Now only the logger knows that Bugsnag is being used.

If we later change services:

-------------------code----------------------
Application
     ↓
   Logger
     ↓
   Sentry
-------------------code----------------------

The rest of the application doesn't need to change.

This is an example of **separation of concerns** and **abstraction**.

---

# 6. Create `logger.js`

Go to the utility folder:

-------------------code----------------------
utility/
-------------------code----------------------

Create:

-------------------code----------------------
logger.js
-------------------code----------------------

So:

-------------------code----------------------
utility/
└── logger.js
-------------------code----------------------

---

# 7. Import Bugsnag

Inside `logger.js`:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";
-------------------code----------------------

This file will be the only place where the application directly communicates with Bugsnag.

---

# 8. Create the `log()` Function

Create a function that receives an error:

-------------------code----------------------
const log = error => {
  Bugsnag.notify(error);
};
-------------------code----------------------

The application can now simply call:

-------------------code----------------------
logger.log(error);
-------------------code----------------------

instead of:

-------------------code----------------------
Bugsnag.notify(error);
-------------------code----------------------

---

# 9. Create the `start()` Function

We also want to hide the Bugsnag initialization.

-------------------code----------------------
const start = () => {
  Bugsnag.start();
};
-------------------code----------------------

Now the rest of the application doesn't need to know how Bugsnag is initialized.

---

# 10. Export the Logger

Export both functions:

-------------------code----------------------
export default {
  log,
  start,
};
-------------------code----------------------

The complete `logger.js` is therefore:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

const log = error => {
  Bugsnag.notify(error);
};

const start = () => {
  Bugsnag.start();
};

export default {
  log,
  start,
};
-------------------code----------------------

---

# 11. Update `App.js`

Previously, `App.js` directly communicated with Bugsnag:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

Bugsnag.start();
-------------------code----------------------

We don't want this anymore.

Instead, import our logger:

-------------------code----------------------
import logger from "./utility/logger";
-------------------code----------------------

Then initialize it:

-------------------code----------------------
logger.start();
-------------------code----------------------

The architecture becomes:

-------------------code----------------------
App.js
  ↓
logger.start()
  ↓
Bugsnag.start()
-------------------code----------------------

---

# 17. Important Difference: Logging vs Error Reporting

Don't think of this as simply replacing every `console.log()`.

A useful distinction is:

### Development debugging

-------------------code----------------------
console.log(value);
-------------------code----------------------

Useful for temporary debugging.

### Production error reporting

-------------------code----------------------
logger.log(error);
-------------------code----------------------

Used when an actual error needs to be monitored remotely.

For example:

-------------------code----------------------
try {
  await cache.store(data);
} catch (error) {
  logger.log(error);
}
-------------------code----------------------

This sends the error to the reporting service.

---

# 18. Best Practices

## 18.1 Keep Bugsnag behind your own abstraction

Prefer:

-------------------code----------------------
logger.log(error);
-------------------code----------------------

over:

-------------------code----------------------
Bugsnag.notify(error);
-------------------code----------------------

throughout the application.

Only `logger.js` should know which error-reporting provider you're using.

---

## 18.2 Don't leave test errors in production

Remove:

-------------------code----------------------
logger.log(new Error("Error in App"));
-------------------code----------------------

after testing.

---

## 18.3 Don't rely exclusively on console logging

`console.log()` is useful during development, but it isn't sufficient for monitoring errors in a distributed production application.

---

## 18.4 Use source maps for production builds

Source maps make production stack traces much easier to understand.

---

## 18.5 Avoid exposing sensitive information

Be careful about sending:

-------------------code----------------------
passwords
authentication tokens
private personal information
API secrets
-------------------code----------------------

as diagnostic data.

Error reporting should contain enough information to debug the problem without unnecessarily exposing sensitive data.

---

                /        \
          start()       log()
             |             |
             v             v
       Bugsnag.start()  Bugsnag.notify()
-------------------code----------------------

This is much cleaner than having Bugsnag scattered throughout the application.

# 20. Full Final Code

## `utility/logger.js`

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

const log = error => {
  Bugsnag.notify(error);
};

const start = () => {
  Bugsnag.start();
};

export default {
  log,
  start,
};
-------------------code----------------------

## `App.js` — relevant final integration

-------------------code----------------------
import React from "react";
import logger from "./utility/logger";

const App = () => {
  logger.start();

  // Your existing App component logic goes here.

  return (
    // Your existing application JSX
  );
};

export default App;
-------------------code----------------------

For your actual project, **keep your existing `App.js` code** and replace the direct Bugsnag initialization with:

-------------------code----------------------
import logger from "./utility/logger";

logger.start();
-------------------code----------------------

Then, in files such as `Cache.js`, replace production error logging:

-------------------code----------------------
console.log(error);
-------------------code----------------------

with:

-------------------code----------------------
logger.log(error);
-------------------code----------------------

# 21. Summary

The main lesson is:

-------------------code----------------------
console.log()
    ↓
Good for development
-------------------code----------------------

but:

-------------------code----------------------
Production error
    ↓
Logger
    ↓
Bugsnag
    ↓
Developer dashboard
-------------------code----------------------

The important implementation steps are:

1. Install and configure Bugsnag.
2. Create `utility/logger.js`.
3. Put `Bugsnag.start()` inside `logger.start()`.
4. Put `Bugsnag.notify()` inside `logger.log()`.
5. Use `logger.start()` from `App.js`.
6. Use `logger.log(error)` when reporting errors.
7. Configure source maps for production builds.
8. Remove temporary test errors.
9. Avoid sending sensitive information.
10. Keep the error-reporting provider hidden behind the logger abstraction.

**Key concept to remember:**

> The application should depend on your `logger` abstraction, not directly on Bugsnag.
