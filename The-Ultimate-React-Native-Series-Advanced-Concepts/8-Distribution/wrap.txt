*** 2- App Icon ***
# App Icon Configuration in Expo

## 1. Overview

Before creating and distributing the application, we need to prepare some important production assets.

The **first step is configuring a proper app icon**.

Expo makes this relatively simple because we provide **one high-resolution icon**, and Expo can generate the required sizes for different platforms.

---

# 2. App Icon Requirements

The lecture specifies the following requirements for the main icon:

### File format

The icon should be:

-------------------code----------------------
PNG
-------------------code----------------------

### Dimensions

The icon should be exactly:

-------------------code----------------------
1024 × 1024 pixels
-------------------code----------------------

Both dimensions must be identical.

Correct:

-------------------code----------------------
Width:  1024 px
Height: 1024 px
-------------------code----------------------

Incorrect:

-------------------code----------------------
Width:  1024 px
Height: 1000 px
-------------------code----------------------

The icon should be perfectly square.

---

# 3. Don't Add Rounded Corners

The source icon should **not contain rounded corners**.

Use:

-------------------code----------------------
Square image
    ↓
Expo / platform processing
    ↓
Platform-specific icon
-------------------code----------------------

Don't manually create the rounded corners.

The platform handles the appropriate presentation.

---

# 4. Follow Platform Design Guidelines

The icon should follow the design guidelines for both:

* Apple
* Android

This is important because app stores and operating systems have specific recommendations for application icons.

The general principle is:

-------------------code----------------------
1024 × 1024 PNG
        ↓
Platform guidelines
        ↓
Production app icon
-------------------code----------------------

---

# 5. Add the Icon to the Assets Folder

Place the icon inside your project's `assets` directory.

For example:

-------------------code----------------------
project/
├── assets/
│   ├── icon.png
│   └── ...
├── app.json
└── ...
-------------------code----------------------

In the lecture, the provided icon represents the letter **D**, referring to the app "Done."

---

# 6. Configure the Icon in `app.json`

Open:

-------------------code----------------------
app.json
-------------------code----------------------

Expo projects normally contain an `icon` property inside the Expo configuration.

Example:

-------------------code----------------------
{
  "expo": {
    "icon": "./assets/icon.png"
  }
}
-------------------code----------------------

The important part is:

-------------------code----------------------
"icon": "./assets/icon.png"
-------------------code----------------------

This tells Expo where the application's main icon is located.

---

# 7. How Expo Handles the Icon

One of the major advantages of Expo's managed workflow is that you don't have to manually create every icon size.

You provide:

-------------------code----------------------
1024 × 1024 icon
-------------------code----------------------

Expo's build system handles the platform-specific icon generation.

Conceptually:

-------------------code----------------------
                icon.png
             1024 × 1024
                   |
                   v
             Expo Build Service
              /            \
             /              \
          iOS              Android
           |                  |
      Required sizes      Required sizes
-------------------code----------------------

This significantly reduces the amount of native configuration you need to manage.

---

# 8. Expo Managed Workflow vs. Ejected/Bare Projects

### Expo Managed Workflow

You provide one main icon:

-------------------code----------------------
assets/icon.png
-------------------code----------------------

and configure:

-------------------code----------------------
{
  "expo": {
    "icon": "./assets/icon.png"
  }
}
-------------------code----------------------

Expo handles much of the platform-specific work.

### Bare / Ejected Workflow

If you move away from Expo's managed workflow, you generally have to deal with native project configuration yourself.

That can mean configuring:

* iOS icon assets
* Android icon resources
* Different resolutions
* Native project settings

The process isn't impossible, but it requires more manual work.

---

# 9. Why Expo Makes This Easier

The main advantage is **less native configuration**.

Without Expo:

-------------------code----------------------
Create icon sizes
       ↓
Configure iOS
       ↓
Configure Android
       ↓
Maintain native assets
-------------------code----------------------

With Expo:

-------------------code----------------------
Create one 1024 × 1024 PNG
       ↓
Configure app.json
       ↓
Expo handles the rest
-------------------code----------------------

This is one of the conveniences of the managed workflow.

---

# 10. Best Practices

### Icon checklist

Before building your application:

* [ ] PNG format
* [ ] Exactly 1024 × 1024 pixels
* [ ] Width = height
* [ ] No manually added rounded corners
* [ ] High-quality artwork
* [ ] Follow Apple design guidelines
* [ ] Follow Android design guidelines
* [ ] Place the icon in `assets/`
* [ ] Configure its path in `app.json`

### Important

Don't resize the image to different dimensions yourself unless you have a specific reason. The production build system can generate the required platform-specific versions.

*** 4- Optimizing JavaScript Bundle ***
# Optimizing Production Assets in an Expo App

## 1. Why Do We Need to Optimize Assets?

When we build the app for production, assets such as images are bundled into the application.

For example:

-------------------code----------------------
assets/
├── logo.png
├── couch.jpg
├── chair.jpg
└── jacket.jpg
-------------------code----------------------

These files can increase the final application size.

The goal is:

> Keep only the assets that are absolutely necessary when the app starts.

Anything that isn't immediately required should preferably be downloaded later from the internet/server.

---

## 2. Remove Unnecessary Assets

Earlier in the course, some images were used as temporary data before connecting the application to the backend.

For example:

-------------------code----------------------
couch.jpg
chair.jpg
jacket.jpg
-------------------code----------------------

Once the application gets its data from the backend, these images are no longer needed.

### Step

Delete unnecessary files:

-------------------code----------------------
assets/
├── logo.png
└── other-essential-assets
-------------------code----------------------

This reduces the size of the production application.

### Important Rule

Before building:

1. Open the `assets` folder.
2. Identify which files are actually required at startup.
3. Delete unused or obsolete files.
4. Move remotely available content to the server/CDN when appropriate.

---

# 3. Install `sharp-cli`

After removing unnecessary assets, we should optimize the remaining images.

The lecture uses `sharp-cli`.

Install it globally:

-------------------code----------------------
npm install -g sharp-cli
-------------------code----------------------

### What is `sharp-cli`?

`sharp-cli` is a command-line tool based on the Sharp image-processing library.

It can optimize images and reduce their file size while maintaining good visual quality.

---

# 4. Optimize Expo Assets

After installing `sharp-cli`, run:

-------------------code----------------------
npx expo-optimize
-------------------code----------------------

The optimization process uses Sharp behind the scenes to reduce the size of the images.

For example:

-------------------code----------------------
npx expo-optimize
-------------------code----------------------

The tool processes the assets and reports how much space was saved.

Example:

-------------------code----------------------
Optimizing assets...

logo.png    saved: 20 KB
image1.jpg  saved: 50 KB
image2.jpg  saved: 58 KB

Total saved: 128 KB
-------------------code----------------------

The exact output will depend on your project.

---

# 5. What Happens During Optimization?

Conceptually:

-------------------code----------------------
Original image
      |
      v
   Sharp
      |
      v
Optimized image
      |
      v
Smaller production bundle
-------------------code----------------------

The important point is that the image is compressed/optimized without noticeably reducing its visual quality.

---

# 6. Why Asset Optimization Matters

In the example from the lecture, the optimization saved approximately:

-------------------code----------------------
128 KB
-------------------code----------------------

For a small application, this isn't a huge amount.

However, in a larger application you may have:

* Dozens or hundreds of images
* Large PNG files
* Background images
* Icons
* Fonts
* Other bundled resources

The savings can become significant.

For example:

-------------------code----------------------
100 images × 200 KB
= 20 MB
-------------------code----------------------

Reducing each image by even 30% could save several megabytes.

---

# 7. Best Practices

### 7.1 Don't bundle everything

Only bundle assets that are required immediately.

Bad:

-------------------code----------------------
assets/
├── 100 product images
├── 50 profile images
├── backgrounds
├── unused images
└── temporary test images
-------------------code----------------------

Better:

-------------------code----------------------
assets/
├── app-icon.png
├── splash.png
└── other startup-critical assets
-------------------code----------------------

Download user/content-specific images from your backend when needed.

---

### 7.2 Delete development leftovers

Before production, check for:

-------------------code----------------------
test images
temporary files
unused icons
old screenshots
sample data
unused fonts
-------------------code----------------------

They should not unnecessarily be included in the final application.

---

### 7.3 Optimize images before building

A good production workflow is:

-------------------code----------------------
Remove unused assets
        ↓
Optimize remaining assets
        ↓
Test the application
        ↓
Create production build
-------------------code----------------------

---

### 7.4 Don't sacrifice quality unnecessarily

The objective isn't simply:

> "Make every image as small as possible."

Instead:

> "Use the smallest reasonable file size while maintaining acceptable quality."

---

# 10. Summary

The production asset optimization process is:

1. **Remove unnecessary assets**

   * Delete old/test images such as `couch.jpg`, `chair.jpg`, and `jacket.jpg`.

2. **Keep only essential startup assets**

   * Don't bundle content that can be downloaded from the backend.

3. **Install Sharp CLI**

-------------------code----------------------
npm install -g sharp-cli
-------------------code----------------------

4. **Optimize Expo assets**

-------------------code----------------------

-------------------code----------------------

5. **Check the reported savings**

   * Larger projects can benefit significantly from image optimization.

6. **Build only after the assets are cleaned and optimized.**

### Key idea

> **Smaller bundled assets = smaller application size and potentially faster installation/startup.**

*** 5- Error Reporting ***
# Error Reporting in Production with Bugsnag

## 1. The Problem with `console.log`

During development, we can see errors in the terminal:

-------------------code----------------------
console.log(error);
-------------------code----------------------

For example, in `Cache.js`:

-------------------code----------------------
try {
  // some operation
} catch (error) {
  console.log(error);
}
-------------------code----------------------

This works while developing locally.

However, after publishing the application to the App Store or Google Play, we don't have access to the user's terminal.

Therefore:

-------------------code----------------------
Development
    ↓
console.log()
    ↓
Terminal
-------------------code----------------------

But in production:

-------------------code----------------------
Production App
    ↓
Error
    ↓
Error reporting service
    ↓
Developer dashboard
-------------------code----------------------

We need an **error reporting service**.

---

# 2. Error Reporting Tools

The lecture introduces two popular options:

* Sentry
* Bugsnag

Bugsnag can report both handled and unhandled errors and can provide diagnostic information such as:

* Device information
* OS version
* React Native / Expo versions
* Date and time
* Error stack trace
* Application release
* Error frequency
* User information
* Error timeline

The important concept is that production errors are collected remotely so developers can investigate them.

---

# 3. Install Bugsnag for Expo

The lecture uses Bugsnag's Expo integration.

The CLI installation command is provided by Bugsnag during project setup.

The general process is:

-------------------code----------------------bash
npx @bugsnag/expo-cli init
-------------------code----------------------

During installation, the CLI asks several questions.

### Question 1: Install Bugsnag?

Answer:

-------------------code----------------------
Yes
-------------------code----------------------

### Question 2: Version

Choose the latest version.

### Question 3: Package manager

Choose:

-------------------code----------------------
npm
-------------------code----------------------

or Yarn if that's what your project uses.

### Question 4: API key

Bugsnag provides an API key from the project dashboard.

The API key allows the application to communicate with Bugsnag.

Important:

**Never expose or commit sensitive credentials unnecessarily.** Follow the current Bugsnag/Expo configuration guidance for production secrets.

---

# 4. Automatically Modify `App.js`

The Bugsnag CLI can add the required initialization code automatically.

Conceptually, it adds something similar to:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

Bugsnag.start();
-------------------code----------------------

Now Bugsnag is initialized when the application starts.

However, the lecture makes an important architectural improvement:

> We don't want the rest of the application to communicate directly with Bugsnag.

Instead, we create our own abstraction.

---

# 5. Why Use an Abstraction?

Imagine that today we use:

-------------------code----------------------
Bugsnag
-------------------code----------------------

but later we decide to switch to:

-------------------code----------------------
Sentry
-------------------code----------------------

If every file directly uses Bugsnag:

-------------------code----------------------
Bugsnag.notify(error);
-------------------code----------------------

we would have to modify many files.

Instead:

-------------------code----------------------
Application
     ↓
   Logger
     ↓
  Bugsnag
-------------------code----------------------

Now only the logger knows that Bugsnag is being used.

If we later change services:

-------------------code----------------------
Application
     ↓
   Logger
     ↓
   Sentry
-------------------code----------------------

The rest of the application doesn't need to change.

This is an example of **separation of concerns** and **abstraction**.

---

# 6. Create `logger.js`

Go to the utility folder:

-------------------code----------------------
utility/
-------------------code----------------------

Create:

-------------------code----------------------
logger.js
-------------------code----------------------

So:

-------------------code----------------------
utility/
└── logger.js
-------------------code----------------------

---

# 7. Import Bugsnag

Inside `logger.js`:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";
-------------------code----------------------

This file will be the only place where the application directly communicates with Bugsnag.

---

# 8. Create the `log()` Function

Create a function that receives an error:

-------------------code----------------------
const log = error => {
  Bugsnag.notify(error);
};
-------------------code----------------------

The application can now simply call:

-------------------code----------------------
logger.log(error);
-------------------code----------------------

instead of:

-------------------code----------------------
Bugsnag.notify(error);
-------------------code----------------------

---

# 9. Create the `start()` Function

We also want to hide the Bugsnag initialization.

-------------------code----------------------
const start = () => {
  Bugsnag.start();
};
-------------------code----------------------

Now the rest of the application doesn't need to know how Bugsnag is initialized.

---

# 10. Export the Logger

Export both functions:

-------------------code----------------------
export default {
  log,
  start,
};
-------------------code----------------------

The complete `logger.js` is therefore:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

const log = error => {
  Bugsnag.notify(error);
};

const start = () => {
  Bugsnag.start();
};

export default {
  log,
  start,
};
-------------------code----------------------

---

# 11. Update `App.js`

Previously, `App.js` directly communicated with Bugsnag:

-------------------code----------------------
import Bugsnag from "@bugsnag/expo";

Bugsnag.start();
-------------------code----------------------

We don't want this anymore.

Instead, import our logger:

-------------------code----------------------
import logger from "./utility/logger";
-------------------code----------------------

Then initialize it:

-------------------code----------------------
logger.start();
-------------------code----------------------

The architecture becomes:

-------------------code----------------------
App.js
  ↓
logger.start()
  ↓
Bugsnag.start()
-------------------code----------------------

---

# 17. Important Difference: Logging vs Error Reporting

Don't think of this as simply replacing every `console.log()`.

A useful distinction is:

### Development debugging

-------------------code----------------------
console.log(value);
-------------------code----------------------

Useful for temporary debugging.

### Production error reporting

-------------------code----------------------
logger.log(error);
-------------------code----------------------

Used when an actual error needs to be monitored remotely.

For example:

-------------------code----------------------
try {
  await cache.store(data);
} catch (error) {
  logger.log(error);
}
-------------------code----------------------

This sends the error to the reporting service.

---

# 18. Best Practices

## 18.1 Keep Bugsnag behind your own abstraction

Prefer:

-------------------code----------------------
logger.log(error);
-------------------code----------------------

over:

-------------------code----------------------
Bugsnag.notify(error);
-------------------code----------------------

throughout the application.

Only `logger.js` should know which error-reporting provider you're using.

---

## 18.2 Don't leave test errors in production

Remove:

-------------------code----------------------
logger.log(new Error("Error in App"));
-------------------code----------------------

after testing.

---

## 18.3 Don't rely exclusively on console logging

`console.log()` is useful during development, but it isn't sufficient for monitoring errors in a distributed production application.

---

## 18.4 Use source maps for production builds

Source maps make production stack traces much easier to understand.

---

## 18.5 Avoid exposing sensitive information

Be careful about sending:

-------------------code----------------------
passwords
authentication tokens
private personal information
API secrets
-------------------code----------------------

as diagnostic data.

Error reporting should contain enough information to debug the problem without unnecessarily exposing sensitive data.

---

After this refactoring:

                     |

                  Logger
                 /      \
                /        \
          start()       log()
             |             |
             v             v
       Bugsnag.start()  Bugsnag.notify()
-------------------code----------------------

This is much cleaner than having Bugsnag scattered throughout the application.

# Managing Configuration Settings for Different Environments

## 1. Why Do We Need Environment Settings?

Most applications run in multiple environments:

1. **Development** — when building and testing locally.
2. **Staging** — a testing environment that is closer to production.
3. **Production** — the real application used by users.

Each environment can have different configuration values.

### Example: API URL

During development, our app may communicate with a local backend:

-------------------code----------------------
http://localhost:9000/api
-------------------code----------------------

But when the application is released, we don't want the production app to communicate with our local computer.

Instead:

-------------------code----------------------
Development → Local backend
Staging     → Staging backend
Production  → Cloud/production backend
-------------------code----------------------

Therefore, we need a centralized way to manage these settings.

---

# 2. Create a Configuration Folder

Create a folder called:

-------------------code----------------------
config
-------------------code----------------------

Then create:

-------------------code----------------------
config/settings.js
-------------------code----------------------

The project structure becomes:

-------------------code----------------------
project/
├── config/
│   └── settings.js
├── api/
│   └── client.js
├── App.js
└── ...
-------------------code----------------------

The purpose of `settings.js` is to keep environment-specific configuration in one place.

---

# 3. Define Settings for Each Environment

Inside `settings.js`, create an object containing settings for:

* Development
* Staging
* Production

### Code

-------------------code----------------------
const settings = {
  dev: {
    API_URL: "http://localhost:9000/api",
  },

  staging: {
    API_URL: "http://localhost:9000/api",
  },

  prod: {
    API_URL: "http://localhost:9000/api",
  },
};
-------------------code----------------------

For now, all three URLs are the same because the backend has not yet been deployed separately.

Later they might look like:

-------------------code----------------------
const settings = {
  dev: {
    API_URL: "http://localhost:9000/api",
  },

  staging: {
    API_URL: "https://staging.example.com/api",
  },

  prod: {
    API_URL: "https://api.example.com/api",
  },
};
-------------------code----------------------

This allows the rest of the application to use one configuration interface without hard-coding URLs everywhere.

---

# 4. Detect the Current Environment

Now we need to determine which environment the application is currently running in.

The lecture uses Expo's `Constants` and React Native's `__DEV__` global variable.

Import `Constants`:

-------------------code----------------------
import Constants from "expo-constants";
-------------------code----------------------

---

# 5. Detect Development Mode

React Native provides a global variable:

-------------------code----------------------
__DEV__
-------------------code----------------------

When the application is running locally in development mode:

-------------------code----------------------
__DEV__ === true
-------------------code----------------------

So we can write:

-------------------code----------------------
if (__DEV__) {
  return settings.dev;
}
-------------------code----------------------

This means:

-------------------code----------------------
Running locally
      ↓
__DEV__ = true
      ↓
Use settings.dev
-------------------code----------------------

---

# 6. Detect Staging

If `__DEV__` is `false`, the application is no longer running in development mode.

It could be:

* Staging
* Production

The lecture uses the Expo release channel to distinguish between them.

-------------------code----------------------
Constants.manifest.releaseChannel
-------------------code----------------------

If the release channel is `"staging"`:

-------------------code----------------------
if (Constants.manifest.releaseChannel === "staging") {
  return settings.staging;
}
-------------------code----------------------

The idea is:

-------------------code----------------------
__DEV__ = false
       ↓
Check release channel
       ↓
"staging" → use staging settings
-------------------code----------------------

---

# 7. Otherwise Use Production

If the application is not development and the release channel is not staging, the lecture assumes it is production.

-------------------code----------------------
return settings.prod;
-------------------code----------------------

Therefore the complete decision process is:

-------------------code----------------------
                 Start
                   |
              __DEV__?
             /        \
           true       false
            |           |
        settings.dev    |
                        |
              releaseChannel?
                  |
             "staging"?
             /        \
           yes         no
            |           |
    settings.staging  settings.prod
-------------------code----------------------

---

# 8. Create `getCurrentSettings()`

Put the environment detection logic into a function.

-------------------code----------------------
const getCurrentSettings = () => {
  if (__DEV__) {
    return settings.dev;
  }

  if (Constants.manifest.releaseChannel === "staging") {
    return settings.staging;
  }

  return settings.prod;
};
-------------------code----------------------

This keeps the environment-selection logic in one place.

---

# 9. Export the Current Settings

Finally, export the result of `getCurrentSettings()`.

-------------------code----------------------
export default getCurrentSettings();
-------------------code----------------------

Now other files don't need to know whether the application is running in development, staging, or production.

They can simply import:

-------------------code----------------------
import settings from "../config/settings";
-------------------code----------------------

and use:

-------------------code----------------------
settings.API_URL
-------------------code----------------------

---

# 10. Update the API Client

Previously, the API client may have contained a hard-coded URL:

-------------------code----------------------
const client = create({
  baseURL: "http://localhost:9000/api",
});
-------------------code----------------------

This is a problem because the production application would still try to use the development backend.

Instead, import the settings:

-------------------code----------------------
import settings from "../config/settings";
-------------------code----------------------

Then change the base URL:

-------------------code----------------------
const client = create({
  baseURL: settings.API_URL,
});
-------------------code----------------------

Now the API client automatically uses the correct backend.

---

# 11. Why This Is Better

Without centralized configuration:

-------------------code----------------------
const client = create({
  baseURL: "http://localhost:9000/api",
});
-------------------code----------------------

The URL is hard-coded.

With centralized configuration:

-------------------code----------------------
const client = create({
  baseURL: settings.API_URL,
});
-------------------code----------------------

The API client doesn't care which environment is active.

The configuration module handles that decision.

### Result

-------------------code----------------------
Development
    ↓
settings.dev
    ↓
Development API


Staging
    ↓
settings.staging
    ↓
Staging API


Production
    ↓
settings.prod
    ↓
Production API
-------------------code----------------------

This makes the application easier to deploy and maintain.

---

# 12. Important Notes

## 12.1 Don't Hard-Code Environment-Specific Values

Avoid:

-------------------code----------------------
const client = create({
  baseURL: "http://localhost:9000/api",
});
-------------------code----------------------

Prefer:

-------------------code----------------------
const client = create({
  baseURL: settings.API_URL,
});
-------------------code----------------------

---

## 12.2 Keep Configuration Centralized

Instead of putting URLs throughout the application:

-------------------code----------------------
fetch("http://localhost:9000/api/users");
-------------------code----------------------

keep them in:

-------------------code----------------------
config/settings.js
-------------------code----------------------

Then use the configuration wherever needed.

---

## 12.3 Staging Is Useful for Testing

A staging environment is useful for testing a build before releasing it to real users.

Typical setup:

-------------------code----------------------
Development
    ↓
Local development/testing

Staging
    ↓
Pre-production testing

Production
    ↓
Real users
-------------------code----------------------

---

## 12.4 Release Channels

The lecture uses Expo release channels to identify staging versus production.

Conceptually:

-------------------code----------------------
staging release → staging configuration

production release → production configuration
-------------------code----------------------

The exact Expo APIs for release channels have changed in newer Expo versions, so if implementing this lecture in a modern Expo project, verify the current Expo configuration API rather than blindly copying the older course code.

---

# 14. Final Concept

The main idea of this lecture is:

-------------------code----------------------
Environment
     ↓
settings.js
     ↓
Select correct configuration
     ↓
settings.API_URL
     ↓

     ↓

-------------------code----------------------

# Summary

* Applications commonly have **development, staging, and production** environments.
* Each environment can have different settings, especially API URLs.
* Create `config/settings.js` to centralize these settings.
* Define separate objects for `dev`, `staging`, and `prod`.
* Use environment information to select the correct configuration.
* Export the selected configuration.
* Import `settings` into the API client.
* Use `settings.API_URL` instead of hard-coding the backend URL.
* This keeps environment-specific configuration centralized and makes deployment easier.
* The lecture's `Constants.manifest.releaseChannel` approach is from the Expo API used in the course; modern Expo projects may require a different configuration mechanism.

# App Distribution: Expo Publishing and Standalone Builds

## 1. Overview

Once an app is ready for distribution, there are two main approaches discussed in the lecture:

1. **Publish the app through Expo**
2. **Build standalone native binaries for iOS and Android**

The choice depends on the purpose.

### Expo publishing

Useful for:

* Development
* Testing
* Sharing with teammates
* Quickly distributing a new version

### Standalone builds

Useful when:

* Preparing the actual iOS/Android application
* Distributing through the App Store or Google Play
* Creating an installable native application

---

# 2. Option 1: Publish the App Through Expo

Publishing through Expo is much faster than creating native binaries.

The basic workflow is:

-------------------code----------------------
Development
    ↓
Expo publish
    ↓
Expo hosts the project
    ↓
Team members scan QR code
    ↓
Run the app with Expo
-------------------code----------------------

This makes it convenient for a development team because everyone can access the same published version.

---

# 3. Publish Using a Release Channel

The lecture uses a command similar to:

-------------------code----------------------
expo publish --release-channel staging
-------------------code----------------------

The important part is:

-------------------code----------------------
--release-channel staging
-------------------code----------------------

Here, `staging` is the name of the release channel.

For example:

-------------------code----------------------
expo publish --release-channel staging
-------------------code----------------------

You could also use another name:

-------------------code----------------------
expo publish --release-channel testing
-------------------code----------------------

or:

-------------------code----------------------
expo publish --release-channel production
-------------------code----------------------

The release-channel name is chosen by the developer.

---

# 4. What Is a Release Channel?

A release channel allows us to separate different published versions of the application.

For example:

-------------------code----------------------
staging
   ↓
Testing version

production
   ↓
Production version
-------------------code----------------------

This connects with the previous lecture about environment configuration.

Previously, we had:

-------------------code----------------------
if (__DEV__) {
  return settings.dev;
}

if (Constants.manifest.releaseChannel === "staging") {
  return settings.staging;
}

return settings.prod;
-------------------code----------------------

So when we publish with:

-------------------code----------------------
expo publish --release-channel staging
-------------------code----------------------

the application can identify itself as belonging to the `staging` environment.

Conceptually:

-------------------code----------------------
expo publish --release-channel staging
                 ↓
          releaseChannel
                 ↓
             "staging"
                 ↓
        settings.staging
                 ↓
          Staging API
-------------------code----------------------

This allows the same application code to use different backend environments.

---

# 5. Expo Project Page

After publishing, Expo provides a project page.

The lecture gives an example conceptually similar to:

-------------------code----------------------
expo.io/<account>/<project>
-------------------code----------------------

The project page contains information about the published application.

It can also provide a QR code.

---

# 6. Sharing the Application With the Team

One major advantage of Expo publishing is how quickly the application can be shared.

A team member can:

1. Open the Expo project page.
2. Scan the QR code.
3. Open the application through Expo.
4. Run the published version.

Conceptually:

-------------------code----------------------
Developer
    ↓
Publishes application
    ↓
Expo
    ↓
QR Code
    ↓
Team member
    ↓
Runs application
-------------------code----------------------

This avoids repeatedly building native iOS and Android binaries during development.

---

# 7. Why Use Expo Publishing During Development?

Building a native application can take considerably more time than publishing an Expo update.

For example:

-------------------code----------------------
Expo publishing
     ↓
Fast
     ↓
Good for testing and development
-------------------code----------------------

Compared with:

-------------------code----------------------
Native build
     ↓
Build iOS binary
Build Android binary
     ↓
More time and setup
-------------------code----------------------

Therefore, Expo publishing is particularly convenient when the team needs to test the latest version quickly.

# Building Standalone Apps with Expo Build Service

## 1. Why Do We Need Standalone Apps?

Publishing an application to Expo is convenient for **development and testing**.

However, it is not ideal for the final users of the application because they would need the Expo client to run the app.

For a real production application, we want users to install:

* An iOS application
* An Android application

directly on their devices.

Therefore:

-------------------code----------------------
Expo Publishing
      ↓
Development / Testing
      ↓
Expo client

Standalone Build
      ↓
Production
      ↓
iOS / Android app
-------------------code----------------------

---

# 2. What Is a Standalone Binary?

A standalone binary is a native application package that can be installed on a device.

Conceptually:

-------------------code----------------------
React Native / Expo project
          ↓
     Build process
       /       \
      ↓         ↓
    iOS      Android
      ↓         ↓
   iOS app   Android app
-------------------code----------------------

These builds can then be submitted to the appropriate app stores.

### iOS

The application can eventually be submitted to:

-------------------code----------------------
Apple App Store
-------------------code----------------------

### Android

The application can eventually be submitted to:

-------------------code----------------------
Google Play Store
-------------------code----------------------

---

# 3. Expo Build Service

Instead of manually building the native applications ourselves, the lecture introduces **Expo's build service**.

The basic idea is:

-------------------code----------------------
Your computer
     ↓
Run Expo build command
     ↓
Expo Build Service
     ↓
Expo's build infrastructure
     ↓
Native application binary
-------------------code----------------------

This means we don't need to perform the entire native build process locally.

The service handles much of the complicated native build process for us.

---

# 4. Why Use Expo's Build Service?

Building native applications manually can involve many configuration steps.

For example, native development may require configuring:

* iOS build tools
* Android build tools
* Certificates
* Provisioning
* Native project settings
* Signing
* Platform-specific configuration

Expo's build service abstracts much of this complexity.

The workflow becomes approximately:

-------------------code----------------------
1. Configure project
        ↓
2. Run build command
        ↓
3. Expo receives project
        ↓
4. Expo performs native build
        ↓
5. Wait for build to finish
        ↓
6. Receive build result
-------------------code----------------------

The important concept is that the build happens on Expo's infrastructure.

-------------------code----------------------

   ↓

The trade-off is:

-------------------code----------------------

-------------------code----------------------

For a course project that can remain managed, staying managed makes the build process simpler.

# 26. Complete Resubmission Workflow

When a new build is required:

-------------------code----------------------
1. Fix the application
        ↓
2. Increase build number
        ↓
3. Create a new iOS build
        ↓
4. Obtain new IPA
        ↓
5. Upload using Transporter
        ↓
6. Wait for App Store Connect processing
        ↓
7. Test with TestFlight if necessary
        ↓
8. Submit new build for review
-------------------code----------------------

This is the cycle you'll repeat whenever a new binary is required.

-------------------code----------------------

-------------------code----------------------

-------------------code----------------------

identifies a particular submitted build.

For example:

-------------------code----------------------

 ├── Build 2

-------------------code----------------------

Then you might release:

-------------------code----------------------

 └── Build 4
-------------------code----------------------

The exact numbering strategy is up to your release process, but every uploaded iOS build needs an appropriate unique/increasing build number.

# Building for Android with Expo

## 1. Android Configuration in `app.json`

Before building the Android version of the app, we need to add Android-specific configuration.

There are two important settings:

1. `package`
2. `versionCode`

Example:

-------------------code----------------------
{
  "expo": {
    "name": "Done With It",
    "slug": "done-with-it",
    "version": "1.0.0",

    "android": {
      "package": "com.codewithmosh.donewithit",
      "versionCode": 1
    }
  }
}
-------------------code----------------------

---

## 2. The `package` Property

-------------------code----------------------
"package": "com.codewithmosh.donewithit"
-------------------code----------------------

The `package` is the **unique identifier of the Android application**.

The usual convention is Reverse DNS notation:

-------------------code----------------------
com.company.application
-------------------code----------------------

For example:

-------------------code----------------------
com.codewithmosh.donewithit
-------------------code----------------------

### Important

This does **not** mean you need to own or operate a website at:

-------------------code----------------------
codewithmosh.com
-------------------code----------------------

It is simply a naming convention for creating a unique application identifier.

### Example

-------------------code----------------------
com.mycompany.donewithit
-------------------code----------------------

The important thing is that the identifier should be unique and should be chosen carefully.

---

# 3. The `version` Property

At the top of `app.json`, we have:

-------------------code----------------------
"version": "1.0.0"
-------------------code----------------------

This represents the **user-facing version** of the application.

For example:

-------------------code----------------------
1.0.0
1.1.0
2.0.0
-------------------code----------------------

Users may see this version in the app store.

---

# 4. The `versionCode` Property

Inside the Android configuration:

-------------------code----------------------
"versionCode": 1
-------------------code----------------------

`versionCode` is an **internal Android/Google Play version number**.

It is different from the user-facing `version`.

For example:

-------------------code----------------------
version     = 1.0.0
versionCode = 1
-------------------code----------------------

For the next submitted build:

-------------------code----------------------
version     = 1.0.1
versionCode = 2
-------------------code----------------------

Then:

-------------------code----------------------
version     = 1.1.0
versionCode = 3
-------------------code----------------------

### Important rule

Every new build submitted as an update must have an appropriately incremented Android build/version code.

Think of it like this:

-------------------code----------------------
version
→ What the user sees

versionCode
→ Internal build number
-------------------code----------------------

---

# 5. Building the Android Application

The original lecture uses the old Expo command:

-------------------code----------------------
expo build:android
-------------------code----------------------

This was the traditional Expo build workflow when the course was recorded.

For a modern Expo project, Android builds are normally created using **EAS Build**:

-------------------code----------------------
eas build --platform android
-------------------code----------------------

So when following this lecture today, use the modern EAS workflow rather than blindly copying the old command.

---

# 6. APK vs Android App Bundle

When creating an Android build, there are two important formats.

## APK

-------------------code----------------------
.apk
-------------------code----------------------

An APK can be installed directly on an Android device.

It is useful for:

* Testing.
* Installing directly on a device.
* Sharing a test build.

Example:

-------------------code----------------------
donewithit.apk
-------------------code----------------------

---

## Android App Bundle

-------------------code----------------------
.aab
-------------------code----------------------

An Android App Bundle is the format normally used for distributing an application through Google Play.

Google Play uses the bundle to generate optimized APKs for different devices/configurations.

### Simple rule

-------------------code----------------------
Testing
→ APK

Google Play production
→ AAB
-------------------code----------------------

---

# 7. Building an APK for Testing

With modern EAS, you can configure a build profile for an APK.

Example `eas.json`:

-------------------code----------------------
{
  "build": {
    "preview": {
      "android": {
        "buildType": "apk"
      }
    }
  }
}
-------------------code----------------------

Then run:

-------------------code----------------------
eas build --platform android --profile preview
-------------------code----------------------

The result is an APK that can be installed on an Android device.

---

# 8. Building an AAB for Google Play

For a production build, configure an App Bundle:

-------------------code----------------------
{
  "build": {
    "production": {
      "android": {
        "buildType": "app-bundle"
      }
    }
  }
}
-------------------code----------------------

Then:

-------------------code----------------------
eas build --platform android --profile production
-------------------code----------------------

This produces an `.aab` suitable for Google Play distribution.

# 9. What Is a Keystore?

Android applications need to be **digitally signed**.

A keystore contains the credentials/keys used for signing the application.

Conceptually:

-------------------code----------------------
Your App
   ↓
Signed with Keystore
   ↓
Android / Google Play
-------------------code----------------------

The keystore establishes the signing identity associated with your application.

---

# 10. Creating or Managing the Keystore

In the old Expo workflow, Expo asked whether you already had a keystore.

If you didn't have one, you could let Expo generate it.

The idea was:

-------------------code----------------------
No existing Keystore
        ↓
Expo creates one
        ↓
Expo uses it to sign the application
-------------------code----------------------

With modern EAS, signing credentials can also be managed through EAS.

For example:

-------------------code----------------------
eas credentials
-------------------code----------------------

This allows you to inspect/manage Android signing credentials for the project.

---

# 11. The Build Queue

When you start an EAS build, the build is performed remotely.

Conceptually:

-------------------code----------------------

      ↓
EAS Build
      ↓
Build Queue
      ↓
Remote Build Machine
      ↓
Android Build
      ↓

-------------------code----------------------

You can monitor the build from the build information provided by EAS.

The important idea from the lecture is that the build does not necessarily happen directly on your computer.

Remote build services may place builds into a queue.

     ↓

     ↓

     ↓

# 14. Should You Leave Expo Because of App Size?

The instructor's main point is:

Moving to a more manually controlled native setup can give you additional control, but it also increases complexity.

Before changing workflows, consider:

-------------------code----------------------

+
Native requirements
+
Build complexity
+
Maintenance
+
Development time
-------------------code----------------------

### Best practice

First measure the actual production build size and identify what is contributing to it.

Do not switch workflows based only on assumptions.

# 15. Why the Keystore Is Extremely Important

The keystore is particularly important when publishing updates.

Suppose your first version is:

-------------------code----------------------
App
versionCode = 1
-------------------code----------------------

and it is signed with:

-------------------code----------------------
Keystore A
-------------------code----------------------

Later you release:

-------------------code----------------------
versionCode = 2
-------------------code----------------------

The update must be signed using the appropriate signing credentials for the existing app.

Conceptually:

-------------------code----------------------
Version 1
    ↓
Keystore A
    ↓
Google Play

Version 2
    ↓
Keystore A
    ↓
Google Play
-------------------code----------------------

The signing credentials are therefore something you must protect and manage carefully.

---

# 16. What Happens If You Lose Your Signing Credentials?

The lecture strongly emphasizes protecting the keystore.

The exact recovery possibilities depend on how your Android signing is configured and on Google Play's current key-management mechanisms.

The important lesson remains:

-------------------code----------------------
Signing credentials
        ↓
Critical production asset
-------------------code----------------------

You should never treat the keystore as an ordinary project file.

---

# 17. Never Commit the Keystore to Git

A keystore contains sensitive signing information.

Do not put it in a public Git repository.

For example, avoid:

-------------------code----------------------
git add donewithit.jks
git commit -m "Add keystore"
git push
-------------------code----------------------

Instead, make sure keystore files are ignored.

Example `.gitignore`:

-------------------code----------------------gitignore
*.jks
*.keystore
-------------------code----------------------

---

# 18. Store the Keystore Securely

Keep secure backups of your signing credentials.

For example:

-------------------code----------------------
Secure Backup
│
├── donewithit.jks
└── signing credentials
-------------------code----------------------

Good storage should be:

* Private.
* Access-controlled.
* Backed up.
* Not publicly accessible.
* Separate from the public source code repository.

Do not store the credentials in:

-------------------code----------------------
GitHub public repository
Public cloud folder
Chat messages
Public documentation
-------------------code----------------------
