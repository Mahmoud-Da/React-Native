# 8. The Problem with Prop Drilling

One approach would be:

-------------------code----------------------
<App user={user}>
-------------------code----------------------

then:

-------------------code----------------------
<Navigator user={user}>
-------------------code----------------------

then:

-------------------code----------------------
<Screen user={user}>
-------------------code----------------------

then:

-------------------code----------------------
<Component user={user}>
-------------------code----------------------

and so on.

---

## What Is Prop Drilling?

Prop drilling means repeatedly passing data through multiple component levels.

Example:

-------------------code----------------------
App
 │
 ▼
Navigator
 │
 ▼
Screen
 │
 ▼
Component
 │
 ▼
Child Component
-------------------code----------------------

Even components that do not need the user object must pass it down.

Problems:

* Repetitive
* Hard to maintain
* Difficult to scale
* Clutters component APIs

---

# 9. Using React Context Instead

React Context solves this problem.

---

## Create Context

-------------------code----------------------
const AuthContext = React.createContext();
-------------------code----------------------

---

## Provide User

In App.js:

-------------------code----------------------
<AuthContext.Provider value={user}>
  <AppNavigator />
</AuthContext.Provider>
-------------------code----------------------

---

## Consume User Anywhere

Any component can access:

-------------------code----------------------
const user = useContext(AuthContext);
-------------------code----------------------

without passing props manually.

---

## Benefits

-------------------code----------------------
No prop drilling
Cleaner code
Easier maintenance
Simple implementation
-------------------code----------------------

---

# 10. Does React Context Replace Redux?

No.

They solve different problems.

---

## React Context Is Good For

Small objects:

-------------------code----------------------
{
  id: 1,
  name: "John"
}
-------------------code----------------------

Examples:

* Authenticated user
* Theme settings
* Language settings
* App configuration

Characteristics:

-------------------code----------------------
Small data
Changes infrequently
Simple sharing
-------------------code----------------------

---

## Redux Is Better For

Large application state.

Examples:

-------------------code----------------------
Shopping carts
Messaging systems
Complex dashboards
Large shared state
-------------------code----------------------

Characteristics:

-------------------code----------------------
Large state tree
Frequent updates
Many subscribers
Complex data flow
-------------------code----------------------

---

# 11. Why Redux Performs Better for Large State

With Context:

-------------------code----------------------
State changes
      │
      ▼
Entire component tree re-renders
-------------------code----------------------

Even components that don't use the changed property may re-render.

---

With Redux:

-------------------code----------------------
State changes
      │
      ▼
Only subscribed components re-render
-------------------code----------------------

This makes Redux more efficient for large, frequently-changing state.

# Full Authentication Flow Example

-------------------code----------------------
const [user, setUser] = useState(null);

const handleLogin = async (credentials) => {
  const token = await authApi.login(credentials);

  const user = decodeToken(token);

  setUser(user);
};

return (
  <AuthContext.Provider value={user}>
    {user ? <AppNavigator /> : <AuthNavigator />}
  </AuthContext.Provider>

1. User submits email and password.
2. App sends a POST request to `/auth`.
3. Server validates credentials.
4. Server returns an authentication token.
5. User information is extracted from the token.

## 1. Goal

Before implementing login in the React Native app, test the authentication endpoint directly using Postman.

This helps verify:

* The backend is working correctly.
* Valid credentials return an authentication token.

   * Returns an error response.

# 6. Understanding Status Code 400

-------------------code----------------------

* Client sent invalid data.
* Request format is correct.
* Credentials are incorrect.

*** 6- Extracting the User from the AuthToken ***
# Understanding JWT (JSON Web Tokens) and Decoding User Information

## 1. Goal

After a successful login, the server returns an authentication token.

Instead of simply logging the token, we want to:

1. Understand what the token contains.
2. Learn how JWT works.
3. Decode the token.
4. Extract the user information.
5. Prepare for storing the user in the application state.

---

# 2. What Is a JWT?

JWT stands for:

-------------------code----------------------
JSON Web Token
-------------------code----------------------

A JWT is a string that contains information about a user and is digitally signed by the server.

Example:

-------------------code----------------------
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
-------------------code----------------------

When a user logs in successfully:

-------------------code----------------------
Email + Password
        ↓
Server Validation
        ↓
JWT Returned
-------------------code----------------------

---

# 3. Inspecting JWT Tokens

Website:

-------------------code----------------------
https://jwt.io
-------------------code----------------------

JWT.io provides a debugger where you can:

* Paste a JWT token.
* Decode it.
* View its contents.

---

# 4. JWT Structure

A JWT contains three sections:

-------------------code----------------------
Header.Payload.Signature
-------------------code----------------------

Example:

-------------------code----------------------
xxxxx.yyyyy.zzzzz
-------------------code----------------------

---

## Section 1: Header

Example:

-------------------code----------------------
{
  "alg": "HS256",
  "typ": "JWT"
}
-------------------code----------------------

Properties:

| Property | Meaning                      |
| -------- | ---------------------------- |
| alg      | Encryption/signing algorithm |
| typ      | Token type (JWT)             |

Normally, frontend applications don't need to use this section.

---

## Section 2: Payload

This is the important part.

Example:

-------------------code----------------------
{
  "_id": "123",
  "name": "Mosh Hamedani",
  "email": "mosh@domain.com",
  "iat": 1590000000
}
-------------------code----------------------

Common properties:

| Property | Meaning             |
| -------- | ------------------- |
| _id      | User ID             |
| name     | User name           |
| email    | User email          |
| iat      | Issued At timestamp |

This payload is what we want to access in our React Native app.

---

## Section 3: Signature

The signature is used to verify that:

-------------------code----------------------
The token has not been modified.
-------------------code----------------------

The server signs the token using:

-------------------code----------------------
HS256 (HMAC SHA256)
-------------------code----------------------

and a secret key.

---

# 5. How JWT Signing Works

Conceptually:

-------------------code----------------------
Header
   +
Payload
   ↓
Base64 Encoding
   ↓
Sign Using Secret Key
   ↓
Signature
-------------------code----------------------

Result:

-------------------code----------------------
Header.Payload.Signature
-------------------code----------------------

---

# 6. Secret Key Security

Backend example:

-------------------code----------------------
jwt.sign(payload, "my-secret-key");
-------------------code----------------------

This works for learning purposes but is bad practice.

Avoid:

-------------------code----------------------
const secret = "my-secret-key";
-------------------code----------------------

inside source code.

### Why?

Anyone with access to:

-------------------code----------------------
Git Repository
-------------------code----------------------

can see the secret.

---

## Correct Approach

Store secrets using environment variables.

Example:

-------------------code----------------------
const secret = process.env.JWT_PRIVATE_KEY;
-------------------code----------------------

Benefits:

* Safer
* Not committed to source control
* Easy to change

---

# 7. Important Security Rule

The payload can be decoded by anyone.

Because of this:

Never store sensitive information inside a JWT.

Bad:

-------------------code----------------------
{
  "password": "12345"
}
-------------------code----------------------

-------------------code----------------------
{
  "creditCard": "1234-5678-9012-3456"
}
-------------------code----------------------

---

Good:

-------------------code----------------------
{
  "_id": "123",
  "name": "Mosh",
  "email": "mosh@domain.com"
}
-------------------code----------------------

Public user information is acceptable.

---

# Important Notes

## Decoding Does Not Require Secret Key

You can decode any JWT without knowing the private key.

-------------------code----------------------
jwtDecode(token);
-------------------code----------------------

works because decoding is not verification.

---

## Validation Requires Secret Key

Only the server can verify whether a token is valid.

-------------------code----------------------
Decode → Anyone
Verify → Server Only
-------------------code----------------------

---

## Never Trust Frontend-Decoded Data Alone

Always verify JWTs on the server before allowing access to protected resources.

---

## Store Only Public Information

Good:

-------------------code----------------------
{
  _id,
  name,
  email
}
-------------------code----------------------

Bad:

-------------------code----------------------
{
  password,
  creditCard
}
