-------------------code----------------------

-------------------code----------------------

-------------------code----------------------

-------------------code----------------------

-------------------code----------------------

# 8. The Problem with Prop Drilling

One approach would be:

-------------------code----------------------
<App user={user}>
-------------------code----------------------

then:

-------------------code----------------------
<Navigator user={user}>
-------------------code----------------------

then:

-------------------code----------------------
<Screen user={user}>
-------------------code----------------------

then:

-------------------code----------------------
<Component user={user}>
-------------------code----------------------

and so on.

---

## What Is Prop Drilling?

Prop drilling means repeatedly passing data through multiple component levels.

Example:

-------------------code----------------------
App
 │
 ▼
Navigator
 │
 ▼
Screen
 │
 ▼
Component
 │
 ▼
Child Component
-------------------code----------------------

Even components that do not need the user object must pass it down.

Problems:

* Repetitive
* Hard to maintain
* Difficult to scale
* Clutters component APIs

---

# 9. Using React Context Instead

React Context solves this problem.

---

## Create Context

-------------------code----------------------
const AuthContext = React.createContext();
-------------------code----------------------

---

## Provide User

In App.js:

-------------------code----------------------
<AuthContext.Provider value={user}>
  <AppNavigator />
</AuthContext.Provider>
-------------------code----------------------

---

## Consume User Anywhere

Any component can access:

-------------------code----------------------
const user = useContext(AuthContext);
-------------------code----------------------

without passing props manually.

---

## Benefits

-------------------code----------------------
No prop drilling
Cleaner code
Easier maintenance
Simple implementation
-------------------code----------------------

---

# 10. Does React Context Replace Redux?

No.

They solve different problems.

---

## React Context Is Good For

Small objects:

-------------------code----------------------
{
  id: 1,
  name: "John"
}
-------------------code----------------------

Examples:

* Authenticated user
* Theme settings
* Language settings
* App configuration

Characteristics:

-------------------code----------------------
Small data
Changes infrequently
Simple sharing
-------------------code----------------------

---

## Redux Is Better For

Large application state.

Examples:

-------------------code----------------------
Shopping carts
Messaging systems
Complex dashboards
Large shared state
-------------------code----------------------

Characteristics:

-------------------code----------------------
Large state tree
Frequent updates
Many subscribers
Complex data flow
-------------------code----------------------

---

# 11. Why Redux Performs Better for Large State

With Context:

-------------------code----------------------
State changes
      │
      ▼
Entire component tree re-renders
-------------------code----------------------

Even components that don't use the changed property may re-render.

---

With Redux:

-------------------code----------------------
State changes
      │
      ▼
Only subscribed components re-render
-------------------code----------------------

This makes Redux more efficient for large, frequently-changing state.

# Full Authentication Flow Example

-------------------code----------------------
const [user, setUser] = useState(null);

const handleLogin = async (credentials) => {
  const token = await authApi.login(credentials);

  const user = decodeToken(token);

  setUser(user);
};

return (
  <AuthContext.Provider value={user}>
    {user ? <AppNavigator /> : <AuthNavigator />}
  </AuthContext.Provider>
);
-------------------code----------------------

This lecture explains how authentication works at the application architecture level.

Key concepts:

1. User submits email and password.
2. App sends a POST request to `/auth`.
3. Server validates credentials.
4. Server returns an authentication token.
5. User information is extracted from the token.
6. The user object is stored in app state.
7. Navigation is determined by whether the user exists.

9. Prop drilling should be avoided.
10. Redux is useful only for large, frequently changing shared state, while React Context is ideal for authentication data.

# Authentication API Testing with Postman and Creating `auth.js`

## 1. Goal

Before implementing login in the React Native app, test the authentication endpoint directly using Postman.

This helps verify:

* The backend is working correctly.
* Valid credentials return an authentication token.
* Invalid credentials return an error.
* The API contract is understood before connecting the frontend.

When a user logs in:

1. User enters email and password.

-------------------code----------------------

-------------------code----------------------

3. Server validates credentials.
4. If valid:

   * Returns an authentication token.
5. If invalid:

   * Returns an error response.

# 6. Understanding Status Code 400

HTTP Status:

-------------------code----------------------

-------------------code----------------------

Meaning:

* Client sent invalid data.
* Request format is correct.
* Credentials are incorrect.

This follows common REST API conventions.

*** 6- Extracting the User from the AuthToken ***
# Understanding JWT (JSON Web Tokens) and Decoding User Information

## 1. Goal

After a successful login, the server returns an authentication token.

Instead of simply logging the token, we want to:

1. Understand what the token contains.
2. Learn how JWT works.
3. Decode the token.
4. Extract the user information.
5. Prepare for storing the user in the application state.

---

# 2. What Is a JWT?

JWT stands for:

-------------------code----------------------
JSON Web Token
-------------------code----------------------

A JWT is a string that contains information about a user and is digitally signed by the server.

Example:

-------------------code----------------------
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
-------------------code----------------------

When a user logs in successfully:

-------------------code----------------------
Email + Password
        ↓
Server Validation
        ↓
JWT Returned
-------------------code----------------------

---

# 3. Inspecting JWT Tokens

Website:

-------------------code----------------------
https://jwt.io
-------------------code----------------------

JWT.io provides a debugger where you can:

* Paste a JWT token.
* Decode it.
* View its contents.

---

# 4. JWT Structure

A JWT contains three sections:

-------------------code----------------------
Header.Payload.Signature
-------------------code----------------------

Example:

-------------------code----------------------
xxxxx.yyyyy.zzzzz
-------------------code----------------------

---

## Section 1: Header

Example:

-------------------code----------------------
{
  "alg": "HS256",
  "typ": "JWT"
}
-------------------code----------------------

Properties:

| Property | Meaning                      |
| -------- | ---------------------------- |
| alg      | Encryption/signing algorithm |
| typ      | Token type (JWT)             |

Normally, frontend applications don't need to use this section.

---

## Section 2: Payload

This is the important part.

Example:

-------------------code----------------------
{
  "_id": "123",
  "name": "Mosh Hamedani",
  "email": "mosh@domain.com",
  "iat": 1590000000
}
-------------------code----------------------

Common properties:

| Property | Meaning             |
| -------- | ------------------- |
| _id      | User ID             |
| name     | User name           |
| email    | User email          |
| iat      | Issued At timestamp |

This payload is what we want to access in our React Native app.

---

## Section 3: Signature

The signature is used to verify that:

-------------------code----------------------
The token has not been modified.
-------------------code----------------------

The server signs the token using:

-------------------code----------------------
HS256 (HMAC SHA256)
-------------------code----------------------

and a secret key.

---

# 5. How JWT Signing Works

Conceptually:

-------------------code----------------------
Header
   +
Payload
   ↓
Base64 Encoding
   ↓
Sign Using Secret Key
   ↓
Signature
-------------------code----------------------

Result:

-------------------code----------------------
Header.Payload.Signature
-------------------code----------------------

---

# 6. Secret Key Security

Backend example:

-------------------code----------------------
jwt.sign(payload, "my-secret-key");
-------------------code----------------------

This works for learning purposes but is bad practice.

Avoid:

-------------------code----------------------
const secret = "my-secret-key";
-------------------code----------------------

inside source code.

### Why?

Anyone with access to:

-------------------code----------------------
Git Repository
-------------------code----------------------

can see the secret.

---

## Correct Approach

Store secrets using environment variables.

Example:

-------------------code----------------------
const secret = process.env.JWT_PRIVATE_KEY;
-------------------code----------------------

Benefits:

* Safer
* Not committed to source control
* Easy to change

---

# 7. Important Security Rule

The payload can be decoded by anyone.

Because of this:

Never store sensitive information inside a JWT.

Bad:

-------------------code----------------------
{
  "password": "12345"
}
-------------------code----------------------

-------------------code----------------------
{
  "creditCard": "1234-5678-9012-3456"
}
-------------------code----------------------

---

Good:

-------------------code----------------------
{
  "_id": "123",
  "name": "Mosh",
  "email": "mosh@domain.com"
}
-------------------code----------------------

Public user information is acceptable.

---

# Important Notes

# Authentication with React Context (Storing the Current User Globally)

## 1. Goal

After successfully logging in and decoding the JWT token, we now need to:

1. Store the authenticated user in the root App component.
2. Make the user available throughout the entire application.
3. Avoid prop drilling.
4. Switch between authenticated and unauthenticated navigation automatically.

---

# 2. The Problem: Prop Drilling

After login, we have a user object:

-------------------code----------------------
{
  userId: 1,
  name: "Mosh",
  email: "mosh@domain.com"
}
-------------------code----------------------

Many screens may need access to this object:

* Account Screen
* Listings Screen
* Messages Screen
* Settings Screen

Passing the user through every component manually is called:

**Prop Drilling**

Example:

-------------------code----------------------
<App user={user}>
  <Navigator user={user}>
    <Screen user={user}>
      <Component user={user} />
    </Screen>
  </Navigator>
</App>
-------------------code----------------------

This becomes difficult to maintain.

---

# 3. Solution: React Context

React Context allows us to:

* Store shared data in one place.
* Access it from any component.
* Avoid prop drilling.

For authentication, Context is a perfect choice because:

* User data is small.
* User data rarely changes.

import React, { useContext } from "react";
import { StyleSheet, View, FlatList } from "react-native";

import { ListItem, ListItemSeparator } from "../components/lists";
import colors from "../config/colors";
import Icon from "../components/Icon";
import routes from "../navigation/routes";
import Screen from "../components/Screen";
import AuthContext from "../auth/context";

const menuItems = [
  {
    title: "My Listings",
    icon: {
      name: "format-list-bulleted",
      backgroundColor: colors.primary,
    },
  },
  {
    title: "My Messages",
    icon: {
      name: "email",
      backgroundColor: colors.secondary,
    },
    targetScreen: routes.MESSAGES,
  },
];

function AccountScreen({ navigation }) {
  const { user } = useContext(AuthContext);

  return (
    <Screen style={styles.screen}>
      <View style={styles.container}>
        <ListItem
          title={user.name}
          subTitle={user.email}
          image={require("../assets/mosh.jpg")}
        />
      </View>

      <View style={styles.container}>
        <FlatList
          data={menuItems}
          keyExtractor={(menuItem) => menuItem.title}
          ItemSeparatorComponent={ListItemSeparator}
          renderItem={({ item }) => (
            <ListItem
              title={item.title}
              IconComponent={
                <Icon
                  name={item.icon.name}
                  backgroundColor={item.icon.backgroundColor}
                />
              }
              onPress={() =>
                navigation.navigate(item.targetScreen)
              }
            />
          )}
        />
      </View>

      <ListItem
        title="Log Out"
        IconComponent={
          <Icon
            name="logout"
            backgroundColor="#ffe66d"
          />
        }
      />
    </Screen>
  );
}

const styles = StyleSheet.create({
  screen: {
    backgroundColor: colors.light,
  },
  container: {
    marginVertical: 20,
  },
});

export default AccountScreen;

*** 10- Persisting the Authentication State Across Restarts ***
# Authentication - Persisting Login with Secure Store

## 1. Goal

Previously, authentication only existed in memory.

That meant:

* User logs in successfully.
* User reloads or restarts the app.
* User is logged out automatically.

The solution is to:

1. Store the authentication token securely.
2. Restore it when the app starts.
3. Remove it when the user logs out.

This creates a persistent login experience.

---

# 2. Why Use Secure Store Instead of AsyncStorage?

Authentication tokens are sensitive.

Never store authentication tokens inside AsyncStorage because:

* Data is not encrypted.
* Anyone with device access may read it.

Instead, Expo provides **Secure Store**.

Advantages:

* Encrypted storage
* Designed for passwords and authentication tokens
* Persistent across app restarts
* Easy API

Install it:

-------------------code----------------------
expo install expo-secure-store
-------------------code----------------------

---

# 3. Create an Authentication Storage Layer

Instead of using SecureStore everywhere, create an abstraction.

-------------------code----------------------
app/
    auth/
        storage.js
-------------------code----------------------

Benefits:

* One place to manage tokens
* Easy to modify later
* Cleaner code
* Reusable

---

# 4. Import Secure Store

-------------------code----------------------
import * as SecureStore from "expo-secure-store";
-------------------code----------------------

---

# 5. Create a Storage Key

Avoid hardcoding strings repeatedly.

-------------------code----------------------
const key = "authToken";
-------------------code----------------------

---

# 6. Store the Authentication Token

Create a function:

-------------------code----------------------
const storeToken = async (authToken) => {
  try {
    await SecureStore.setItemAsync(key, authToken);
  } catch (error) {
    console.log("Error storing auth token", error);
  }
};
-------------------code----------------------

Steps:

1. Receive token.
2. Save it securely.
3. Handle errors.

---

# 7. Retrieve the Authentication Token

-------------------code----------------------
const getToken = async () => {
  try {
    return await SecureStore.getItemAsync(key);
  } catch (error) {
    console.log("Error getting auth token", error);
  }
};
-------------------code----------------------

Steps:

1. Read token.
2. Return it.
3. Handle failures.

---

# 8. Remove the Authentication Token

When the user logs out:

-------------------code----------------------
const removeToken = async () => {
  try {
    await SecureStore.deleteItemAsync(key);
  } catch (error) {
    console.log("Error removing auth token", error);
  }
};
-------------------code----------------------

# 16. Important Notes

### Never store JWT tokens in AsyncStorage.

Use Secure Store for sensitive data.

---

### Always abstract storage.

Instead of:

-------------------code----------------------
SecureStore.setItemAsync(...)
-------------------code----------------------

everywhere, use:

-------------------code----------------------
authStorage.storeToken(...)
-------------------code----------------------

---

### Decode the JWT.

The token contains the user information.

-------------------code----------------------
const user = jwtDecode(token);
-------------------code----------------------

No additional API request is needed.

---

### Restore authentication only once.

-------------------code----------------------
useEffect(() => {
    restoreToken();
}, []);
-------------------code----------------------

---

### Remove tokens on logout.

Otherwise the app will automatically log the user back in.

---

### Handle Secure Store errors.

Wrap all storage operations in `try...catch`.

---

# 17. Best Practices

* Store authentication tokens only in Secure Store.
* Keep all authentication storage logic in one module.
* Decode JWT instead of making another request to fetch user info.
* Restore the user automatically when the app starts.
* Remove tokens during logout.
* Handle storage errors gracefully.
* Use React Context for authentication state.

# Authentication - Refactoring Authentication Logic

## 1. Goal

The authentication flow works correctly, but the `App` component has become responsible for too many authentication details.

Previously, `App.js`:

* Read the token from storage.
* Decoded the JWT.
* Set the current user.

This violates the principle of **separation of concerns**.

The goal is to move authentication-related logic into the authentication module so the `App` component only coordinates the process.

---

# 2. The Problem

Previously, `App.js` looked similar to this:

-------------------code----------------------
const restoreToken = async () => {
  const token = await authStorage.getToken();

  if (!token) return;

  setUser(jwtDecode(token));
};
-------------------code----------------------

Notice that `App.js` knows:

* where the token is stored,
* how to retrieve it,
* how to decode it,
* how to create a user object.

These implementation details belong to the authentication layer, not the application entry point.

---

# 3. Apply Separation of Concerns

Think of `App.js` as a manager.

A good manager:

* delegates work,
* doesn't perform every task personally.

Instead of:

-------------------code----------------------

 ├── Read SecureStore
 ├── Decode JWT
 ├── Create User
 └── Set User
-------------------code----------------------

It should simply do:

-------------------code----------------------
App

↓

Ask Auth Module

↓

"Give me the current user."

↓

Receive User

↓

Set User
-------------------code----------------------

The authentication module hides all internal implementation details.

---

# 4. Update auth/storage.js

Previously, this module exported:

-------------------code----------------------
export default {
  storeToken,
  getToken,
  removeToken,
};
-------------------code----------------------

The `getToken()` function exposes too much detail.

Instead, create a higher-level function.

---

-------------------code----------------------

-------------------code----------------------

The authentication module is now responsible for decoding JWTs.

  return null;
};
-------------------code----------------------

This function:

1. Retrieves the token.
2. Decodes it.
3. Returns the user.
4. Returns `null` if no token exists.

The caller never needs to know how this happens.

The lecture simplifies it further.

-------------------code----------------------

  return token ? jwtDecode(token) : null;
};
-------------------code----------------------

This is equivalent but shorter and easier to read.

Instead of exporting `getToken()`:

-------------------code----------------------

Now other modules only interact with users, not raw tokens.

# Authentication - Calling Protected API Endpoints with JWT

## 1. Overview

Many backend endpoints should only be accessible to authenticated users.

Examples:

* Get current user's listings
* Create a listing
* Update a profile
* Delete an account
* Upload images

These endpoints require the client to send a **JSON Web Token (JWT)** with every request.

---

# 2. What Happens Without a Token?

Suppose we call a protected endpoint:

-------------------code----------------------http
GET /api/listings/mine
-------------------code----------------------

Without an authentication token, the server responds with:

-------------------code----------------------http
401 Unauthorized
-------------------code----------------------

Response body:

-------------------code----------------------json
{
  "error": "Access denied. No token provided."
}
-------------------code----------------------

This means:

* The request reached the server.
* The endpoint requires authentication.
* No JWT was included.

---

# 3. Passing the Token Manually

In Postman, add a request header.

-------------------code----------------------http
Key:
x-auth-token
-------------------code----------------------

-------------------code----------------------http
Value:
<your JWT token>
-------------------code----------------------

Example:

-------------------code----------------------http
GET /api/listings/mine

Headers:
x-auth-token: eyJhbGciOiJIUzI1NiIs...
-------------------code----------------------

Now the server recognizes the user and returns the requested data.

---

# 4. Problem with Manual Headers

Imagine an app with:

* 20 API files
* 100 requests

Adding this header manually every time:

-------------------code----------------------
headers: {
    "x-auth-token": token
}
-------------------code----------------------

would become repetitive and error-prone.

Instead, add the token automatically for **every request**.

---

# 5. Solution: Request Transformation

Since **every API request** goes through `client.js`, this is the perfect place to inject the authentication token.

Flow:

-------------------code----------------------
Screen
      ↓
API Module
      ↓
client.js
      ↓
Add JWT Header
      ↓
Server
-------------------code----------------------

Now every request automatically includes the token.

---

# 6. Import Authentication Storage

First, import the storage module.

-------------------code----------------------
import authStorage from "../auth/storage";
-------------------code----------------------

This module stores and retrieves the JWT securely.

---

# 7. Add an Async Request Transform

Apisauce provides a hook that runs before every request.

-------------------code----------------------
apiClient.addAsyncRequestTransform(async (request) => {

});
-------------------code----------------------

This function executes automatically before the request is sent.

---

# 8. Read the Stored Token

Inside the transform:

-------------------code----------------------
const authToken =
    await authStorage.getToken();
-------------------code----------------------

This retrieves the JWT from secure storage.

---

# 9. Handle Missing Tokens

If the user is not logged in:

-------------------code----------------------
if (!authToken)
    return;
-------------------code----------------------

The request proceeds normally without authentication.

This allows public endpoints to continue working.

---

# 10. Attach the Token

If a token exists:

-------------------code----------------------
request.headers["x-auth-token"] =
    authToken;
-------------------code----------------------

Every outgoing request now contains:

-------------------code----------------------http
x-auth-token: eyJhbGciOiJIUzI1Ni...
-------------------code----------------------

No screen has to remember to send it.

---

# 11. Export `getToken()`

Earlier, `storage.js` only exposed higher-level methods.

Now export `getToken()` so `client.js` can retrieve the raw JWT.

-------------------code----------------------
export default {
    storeToken,
    getToken,
    getUser,
    removeToken,
};
-------------------code----------------------

This is the only change required in `storage.js`.

---

# 12. Request Flow

The complete request lifecycle now becomes:

-------------------code----------------------
User logs in
        │
        ▼
JWT stored securely
        │
        ▼
User opens a screen
        │
        ▼
API request starts
        │
        ▼
client.js executes request transform
        │
        ▼
Read JWT from Secure Store
        │
        ▼
Add x-auth-token header
        │
        ▼
Send request
        │
        ▼
Server validates token
        │
        ▼
Return protected data
-------------------code----------------------

Everything happens automatically.

---

# 13. How the Server Validates the Token

### Step 1

Read the request header.

-------------------code----------------------
x-auth-token
-------------------code----------------------

---

### Step 2

If no token exists:

Return:

-------------------code----------------------http
401 Unauthorized
-------------------code----------------------

-------------------code----------------------json
{
    "error": "Access denied. No token provided."
}
-------------------code----------------------

---

### Step 3

If a token exists:

Verify it using the JWT library.

-------------------code----------------------
jsonwebtoken.verify(...)
-------------------code----------------------

The server also uses its **private secret key**.

---

### Step 4

If verification succeeds:

The server extracts the payload.

Example:

-------------------code----------------------json
{
    "_id": "...",
    "name": "Mosh",
    "email": "mosh@domain.com"
}
-------------------code----------------------

The payload is attached to the request.

-------------------code----------------------
request.user
-------------------code----------------------

Now every route can access the current authenticated user.

---

### Step 5

If verification fails:

Return:

-------------------code----------------------http
400 Bad Request
-------------------code----------------------

-------------------code----------------------json
{
    "error": "Invalid token."
}
-------------------code----------------------

---

# 14. Status Codes

| Status Code | Meaning      | Reason                     |
| ----------- | ------------ | -------------------------- |
| **200**     | Success      | Valid token                |
| **400**     | Bad Request  | Invalid or corrupted token |
| **401**     | Unauthorized | No token provided          |

---

# 15. Why This Design Is Better

Instead of doing this everywhere:

-------------------code----------------------
authStorage.getToken()

headers["x-auth-token"] = token
-------------------code----------------------

every API request becomes simply:

-------------------code----------------------
client.get("/listings");
-------------------code----------------------

or

-------------------code----------------------
client.post("/listings", listing);
-------------------code----------------------

The authentication header is added automatically.

---

# 16. Best Practices

### Keep authentication inside the API layer

`client.js` should be responsible for adding authentication headers.

---

### Never hard-code secret keys

The server's JWT signing key should be stored as an **environment variable**, not inside the source code.

---

### Use Secure Storage

On Expo, store JWTs using **SecureStore**, not AsyncStorage.

---

### Keep UI components simple

Screens should never worry about:

* Reading tokens
* Sending headers
* Verifying authentication

Those responsibilities belong to the API and authentication layers.

---

# 17. Full Final Code

## `auth/storage.js`

-------------------code----------------------
import * as SecureStore from "expo-secure-store";
import jwtDecode from "jwt-decode";

const key = "authToken";

const storeToken = async (authToken) => {
  try {
    await SecureStore.setItemAsync(key, authToken);
  } catch (error) {
    console.log("Error storing the auth token", error);
  }
};

const getToken = async () => {
  try {
    return await SecureStore.getItemAsync(key);
  } catch (error) {
    console.log("Error getting the auth token", error);
  }
};

const getUser = async () => {
  const token = await getToken();
  return token ? jwtDecode(token) : null;
};

const removeToken = async () => {
  try {
    await SecureStore.deleteItemAsync(key);
  } catch (error) {
    console.log("Error removing the auth token", error);
  }
};

export default {
  storeToken,
  getToken,
  getUser,
  removeToken,
};
-------------------code----------------------

---

## `api/client.js`

-------------------code----------------------
import { create } from "apisauce";
import cache from "../utility/cache";
import authStorage from "../auth/storage";

const apiClient = create({
  baseURL: "http://192.168.0.14:9000/api",
});

apiClient.addAsyncRequestTransform(async (request) => {
  const authToken = await authStorage.getToken();

  if (!authToken) return;

  request.headers["x-auth-token"] = authToken;
});

const get = apiClient.get;
apiClient.get = async (url, params, axiosConfig) => {
  const response = await get(url, params, axiosConfig);

  if (response.ok) {
    cache.store(url, response.data);
    return response;
  }

  const data = await cache.get(url);
  return data ? { ok: true, data } : response;
};

export default apiClient;
-------------------code----------------------

-------------------code----------------------

    setError(true);

-------------------code----------------------

-------------------code----------------------

result.data
result.problem

# 15. Important Notes

# 17. Important Notes

### Use `position: "absolute"`

Without it, the overlay becomes part of the normal layout and pushes other components.

---

Ensures the overlay appears above the rest of the UI.

---

### Keep the background semi-transparent

-------------------code----------------------

---

### Place overlays outside `Screen`

The `Screen` component often adds safe-area padding or margins.

Overlays should sit above the entire screen, not inside its layout.

---

### Use one reusable component

Instead of creating a different loading indicator for every screen, reuse the same `ActivityIndicator` component.

# 18. Best Practices

* Build loading overlays as reusable components.
* Position overlays absolutely.
* Use `zIndex` so overlays cover all content.
* Make overlays semi-transparent.
* Move overlays outside layout containers like `Screen`.
* Keep the loading state controlled by `useApi`.
