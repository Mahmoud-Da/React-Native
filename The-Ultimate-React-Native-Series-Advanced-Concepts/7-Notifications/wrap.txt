*** 1- Introduction ***
# 1. Introduction: Notifications

This section introduces how to add **push notifications** to a React Native application.

The goal is to extend the existing marketplace-style app so that:

1. A user can contact the owner of a listing.
2. The owner receives a **push notification** on their mobile device.
3. The notification informs them that someone has sent them a message.

The section therefore combines two concepts:

* **Messaging:** sending a message to another user.
* **Push notifications:** notifying that user even when the app is not currently open.

---

# 2. What Is a Push Notification?

A push notification is a message sent from your backend to a user's mobile device.

For example:

-------------------code----------------------
User A
   |
   | Sends message
   v
Backend
   |
   | Push notification
   v
User B's phone
   |
   v
"Someone sent you a message"
-------------------code----------------------

The important point is that the notification is **not simply a React Native component**.

The backend and the mobile device need to communicate through a push notification service.

---

The overall flow will eventually look like this:

### Step 1: User A opens a listing

### Step 2: User A sends a message

-------------------code----------------------

   ↓

-------------------code----------------------

### Step 4: Backend sends a push notification

-------------------code----------------------
Backend
   ↓
Push Notification Service
   ↓

-------------------code----------------------

### Step 5: User B receives the notification

For example:

-------------------code----------------------

-------------------code----------------------

# 6. Important Notes and Best Practices

### 6.1 Push notifications are different from normal API responses

An API response goes directly back to the application that made the request:

-------------------code----------------------
App → Backend → App
-------------------code----------------------

A push notification can reach another device:

-------------------code----------------------
App A → Backend → App B
-------------------code----------------------

---

### 6.2 The recipient needs a way to be identified

The backend needs some information that allows it to send the notification to the correct device.

Typically, this involves storing a **push notification token** associated with the user/device.

Conceptually:

-------------------code----------------------
{
  userId: 123,
  pushToken: "device-specific-token"
}
-------------------code----------------------

The exact implementation will depend on the notification service being used.

---

### 6.3 Don't put notification credentials or secrets in the mobile app

Sensitive credentials should remain on the backend.

The React Native application should not contain private server credentials that could be extracted from the application.

*** 2- Push Notification Services ***
# 1. Push Notification Providers

When implementing push notifications in a React Native / Expo application, there are several services you can choose from.

The lecture focuses on four main options:

1. **Expo Push Notification Service**
2. **OneSignal**
3. **Firebase Cloud Messaging (FCM)**
4. **Amazon Simple Notification Service (SNS)**

---

# 2. Expo Push Notification Service

For an Expo application, **Expo's notification service is the simplest option**.

The main advantage is that Expo hides much of the native complexity involved in push notifications.

Conceptually:

-------------------code----------------------
Your React Native App
        |
        v
Expo Push Notification Service
        |
        v
User's Device
-------------------code----------------------

Instead of configuring many native components yourself, Expo provides an abstraction that makes sending and receiving notifications much easier.

### Main advantages

* Simple setup
* Works well with Expo applications
* Hides much of the native complexity
* Supports both managed and bare/prebuild-style Expo projects
* Free according to the lecture's recording-time information

---

# 3. Other Notification Providers

## 3.1 OneSignal

OneSignal is a dedicated push notification platform.

It provides additional notification-related features, but integrating it can require more native configuration depending on the project setup.

---

## 3.2 Firebase Cloud Messaging

Firebase Cloud Messaging, commonly called **FCM**, is Google's push notification infrastructure.

It is widely used, especially in applications already using Firebase.

---

## 3.3 Amazon SNS

Amazon Simple Notification Service (**SNS**) is Amazon's notification service.

It can be useful when an organization already has an AWS-based infrastructure or requires AWS services for architectural or policy reasons.

---

# 4. Why the Alternatives Can Be More Complicated

The main issue is not that OneSignal, FCM, or SNS are bad services.

The issue is the **additional setup required**, particularly when working with native iOS and Android projects.

The lecture explains that using these alternatives may require leaving the simple Expo workflow and making changes to the native projects.

Conceptually:

-------------------code----------------------
Expo Push Notifications
        |
        v
  Less native setup
        |
        v
    Easier setup
-------------------code----------------------

Compared with:

-------------------code----------------------
Other providers
        |
        v
Native configuration
        |
        v
iOS configuration
+
Android configuration
        |
        v
More setup and maintenance
-------------------code----------------------

If one configuration step is missed, notifications may simply fail to work, making debugging more difficult.

---

# 5. Recommended Choice

For a normal Expo application, the lecture's recommendation is:

> **Use Expo's push notification service unless you have a specific reason to use another provider.**

For example, an organization might have a policy requiring AWS infrastructure. In that situation, Amazon SNS may be required even though Expo would be easier.

So the decision can be summarized as:

| Situation                                  | Recommended approach     |
| ------------------------------------------ | ------------------------ |
| Normal Expo application                    | Expo Notifications       |
| Organization requires AWS                  | Amazon SNS               |
| Existing Firebase infrastructure           | FCM may make sense       |
| Specialized notification platform/features | OneSignal may make sense |

The important principle is:

**Don't introduce unnecessary native complexity if Expo already provides everything your application needs.**

*** 3- Architecture ***

# 1. Overview: How Push Notifications Work

Push notifications can be implemented without Redux.

The lecture explains that there are **four main steps**:

1. Register the device and obtain an Expo Push Token.
2. Store that token on the backend.
3. Send notifications from the backend.
4. Handle notifications received by the app.

The complete flow is:

-------------------code----------------------
Mobile App
    |
    | 1. Register device
    v
Expo
    |
    | Push Token
    v
Mobile App
    |
    | 2. Send token
    v
Backend / Database
    |
    | 3. Send notification
    v
Expo Push Notification Service
    |
    v
Target Device
    |
    | 4. User taps notification
    v
Mobile App
-------------------code----------------------

---

# 2. Step 1: Register the App and Get a Push Token

The first step is to register the application with Expo.

The goal is to obtain an **Expo Push Token**.

A push token is a long string that identifies a particular device/app installation for push notifications.

Conceptually:

-------------------code----------------------
const pushToken = "ExponentPushToken[xxxxxxxxxxxxxxxxxxxx]";
-------------------code----------------------

The important idea is:

-------------------code----------------------
Device
   ↓
Expo registration
   ↓
Push Token
-------------------code----------------------

Once we have this token, the backend can use it to send a notification to that particular device.

---

# 3. Step 2: Store the Push Token on the Server

After obtaining the token, the application should send it to the backend.

The backend then stores it in the database.

For example, a user record could look conceptually like:

-------------------code----------------------
{
  id: 123,
  name: "John",
  email: "john@domain.com",
  expoPushToken: "ExponentPushToken[xxxxxxxxxxxxxxxxxxxx]"
}
-------------------code----------------------

The database therefore associates:

-------------------code----------------------
User
  ↓
Expo Push Token
  ↓
Specific device
-------------------code----------------------

This allows the backend to determine which device should receive a notification.

---

# 8. Important Distinction: Token vs Notification

Don't confuse these two concepts.

### Push Token

Identifies the destination device/app installation.

-------------------code----------------------
"ExponentPushToken[abc123...]"
-------------------code----------------------

### Notification

The actual message sent to that device.

-------------------code----------------------
{
  title: "New Message",
  body: "John sent you a message."
}
-------------------code----------------------

The relationship is:

-------------------code----------------------
Push Token = WHERE to send

Notification = WHAT to send
-------------------code----------------------

# 9. Best Practices

### 9.1 Store tokens on the backend

Don't rely on keeping the push token only inside the mobile app.

The backend needs the token when it wants to send a notification later.

### 9.2 Send notifications from the backend

The backend should control notification delivery because it knows the application's business logic.

### 9.3 Associate tokens with users

A useful conceptual database structure is:

-------------------code----------------------
User
├── id
├── name
├── email
└── expoPushToken
-------------------code----------------------

### 9.4 Think about multiple devices

A user may eventually have:

-------------------code----------------------
User
 ├── iPhone
 ├── iPad
 └── Android device
-------------------code----------------------

In a production application, you may therefore need to associate **multiple push tokens** with one user rather than assuming one token per user.

# 7. Request Notification Permission

First, ask the user for permission.

-------------------code----------------------
const permission = await Permissions.askAsync(
  Permissions.NOTIFICATIONS
);
-------------------code----------------------

Then check whether permission was granted:

-------------------code----------------------
if (!permission.granted) {
  return;
}
-------------------code----------------------

The complete logic is:

-------------------code----------------------
const permission = await Permissions.askAsync(
  Permissions.NOTIFICATIONS
);

if (!permission.granted) {
  return;
}
-------------------code----------------------

### Important

On an emulator/simulator, the permission result may not behave like a real device.

Therefore, test this functionality on an actual phone.

---

# 8. Get the Expo Push Token

Once permission has been granted, request the token:

-------------------code----------------------
const token = await Notifications.getExpoPushTokenAsync();
-------------------code----------------------

The token is a long string similar to:

-------------------code----------------------
ExponentPushToken[xxxxxxxxxxxxxxxxxxxxxxxx]
-------------------code----------------------

This token identifies the destination for push notifications.

---

# 9. App Installation vs Device

An important detail from the lecture:

The token more accurately identifies an **app installation**, rather than simply the physical device.

For example:

-------------------code----------------------
Install App
    ↓
Push Token A
-------------------code----------------------

If the application is deleted and reinstalled:

-------------------code----------------------
Reinstall App
    ↓
Push Token B
-------------------code----------------------

So you should not assume that the token remains permanently unchanged.

If the application is simply launched again without being reinstalled, the same token will normally be returned.

---

# 10. Add Error Handling

Network/device operations can fail, so the registration code should use `try...catch`.

-------------------code----------------------
const registerForPushNotifications = async () => {
  try {
    const permission = await Permissions.askAsync(
      Permissions.NOTIFICATIONS
    );

    if (!permission.granted) {
      return;
    }

    const token = await Notifications.getExpoPushTokenAsync();

    console.log(token);
  } catch (error) {
    console.log("Error getting a push token.", error);
  }
};
-------------------code----------------------

This prevents an error during registration from crashing the application.

import React, { useEffect } from "react";
import { createBottomTabNavigator } from "@react-navigation/bottom-tabs";
import { MaterialCommunityIcons } from "@expo/vector-icons";
import * as Notifications from "expo-notifications";
import * as Device from "expo-device";

import AccountNavigator from "./AccountNavigator";
import FeedNavigator from "./FeedNavigator";
import ListingEditScreen from "../screens/ListingEditScreen";
import NewListingButton from "./NewListingButton";
import routes from "./routes";

const Tab = createBottomTabNavigator();

async function registerForPushNotificationsAsync() {
  try {
    // Push notifications require a physical device.
    if (!Device.isDevice) {
      console.log(
        "Push notifications require a physical device."
      );
      return;
    }

    // Check existing notification permission.
    const { status: existingStatus } =
      await Notifications.getPermissionsAsync();

    let finalStatus = existingStatus;

    // Ask the user for permission if we don't have it yet.
    if (existingStatus !== "granted") {
      const { status } =
        await Notifications.requestPermissionsAsync();

      finalStatus = status;
    }

    // Permission was denied.
    if (finalStatus !== "granted") {
      console.log("Notification permission not granted.");
      return;
    }

    // Get the Expo push notification token.
    const tokenData =
      await Notifications.getExpoPushTokenAsync();

    const token = tokenData.data;

    console.log("Expo Push Token:", token);

    return token;
  } catch (error) {
    console.log(
      "Error getting a push notification token:",
      error
    );
  }
}

async function registerForPushNotificationsAsync() {
  try {
    // Push notifications require a physical device.
    if (!Device.isDevice) {
      console.log(
        "Push notifications require a physical device."
      );
      return;
    }

    // Check existing permission.
    const { status: existingStatus } =
      await Notifications.getPermissionsAsync();

    let finalStatus = existingStatus;

    // Ask for permission if necessary.
    if (existingStatus !== "granted") {
      const { status } =
        await Notifications.requestPermissionsAsync();

      finalStatus = status;
    }

    // Permission denied.
    if (finalStatus !== "granted") {
      console.log(
        "Notification permission not granted."
      );
      return;
    }

    // Get Expo push token.
    const tokenData =
      await Notifications.getExpoPushTokenAsync();

    const token = tokenData.data;

    // Send token to the backend.
    expoPushTokensApi.register(token);
  } catch (error) {
    console.log(
      "Error getting a push notification token:",
      error
    );
  }
}

The important idea is:

> The mobile app does not directly send the push notification. The backend sends it using an Expo SDK.

The flow is:

-------------------code----------------------
Your Backend
     ↓
Expo Server SDK
     ↓
Expo Push Notification Service
     ↓
 ┌───────────────┐
 │               │

 │               │
 ↓               ↓
FCM             APNs
 │               │
 ↓               ↓
Android Device  iPhone
-------------------code----------------------

# 2. Expo Provides SDKs for Different Backends

Expo provides server-side SDKs for different programming languages.

Examples include:

* Node.js
* Python
* Ruby
* Other supported environments

You choose the SDK that matches your backend technology.

For example, if your backend is Node.js:

-------------------code----------------------
Node.js Backend
      ↓
Expo Server SDK
      ↓
Expo Push Service
-------------------code----------------------

If your backend is Python:

-------------------code----------------------

      ↓
Expo Python SDK
      ↓
Expo Push Service
-------------------code----------------------

The important point is that the SDK handles the communication with Expo for you.

# 3. What Happens Behind the Scenes?

Suppose your backend wants to send:

-------------------code----------------------
"Mosh says: Is your jacket still available?"
-------------------code----------------------

Your backend sends an HTTP request to Expo.

-------------------code----------------------
Backend
   |
   | HTTP POST
   ↓
Expo Push Service
-------------------code----------------------

Expo then determines the target device's platform.

### Android

-------------------code----------------------
Backend
   ↓
Expo
   ↓
Firebase Cloud Messaging (FCM)
   ↓
Android Device
-------------------code----------------------

### iOS

-------------------code----------------------
Backend
   ↓
Expo
   ↓
Apple Push Notification Service (APNs)
   ↓
iPhone
-------------------code----------------------

You don't have to manually implement the FCM/APNs communication.

That is one of the major advantages of using Expo's push notification service.

Without Expo, your backend would need to deal with platform-specific notification systems.

Conceptually:

-------------------code----------------------
Your Backend
   ├── Android → FCM
   └── iOS → APNs
-------------------code----------------------

With Expo:

-------------------code----------------------
Your Backend
     ↓
Expo
     ├── Android → FCM
     └── iOS → APNs
-------------------code----------------------

Expo hides much of this complexity.

Your backend only needs to communicate with Expo.

# Handling Received Push Notifications

## 1. Goal

In this lesson, we learn how to detect when a user **taps on a push notification**.

The basic flow is:

1. A push notification arrives.
2. The user taps the notification.
3. Expo triggers a listener.
4. We receive a `notification` object.
5. We can inspect its data.
6. Later, we can use that data to navigate to a specific screen.

---

# 2. Add a Notification Listener

The notification listener should be registered in `AppNavigator`, because this is where we can later control navigation.

Add the listener:

-------------------code----------------------
notifications.addNotificationResponseReceivedListener(
  (notification) => {
    console.log(notification);
  }
);
-------------------code----------------------

The listener receives a notification response object.

---

# 3. Inspect the Notification Object

When the user taps a notification, the object contains information about the notification.

For example, the important part is:

-------------------code----------------------
notification.notification.request.content.data
-------------------code----------------------

This contains the custom JSON data that we included when sending the notification.

For example, if the notification contained:

-------------------code----------------------
{
  "listingId": 123
}
-------------------code----------------------

we can retrieve it with:

-------------------code----------------------
const data =
  notification.notification.request.content.data;

console.log(data);
-------------------code----------------------

This is very useful because we can later use `listingId` to determine which listing screen to open.

---

# 4. `received` vs `selected`

The notification response can indicate how the notification was handled.

### `received`

The notification was received while the app was already in the foreground.

### `selected`

The app was not in the foreground, and the user tapped the notification to open it.

Conceptually:

-------------------code----------------------
App is open
     |
     v
Notification arrives
     |
     v
received
-------------------code----------------------

Whereas:

-------------------code----------------------
App is closed/background
     |
     v
Notification arrives
     |
     v
User taps notification
     |
     v
selected
-------------------code----------------------

The `selected` case is particularly important because this is where we often want to navigate the user to a specific screen.

---

# 5. Remote Notifications

The lesson also introduces the concept of **remote notifications**.

A remote notification is sent from a server to the device.

For example:

-------------------code----------------------
Backend
   |
   v
Expo Push Service
   |
   v
Mobile Device
-------------------code----------------------

The notification we are working with is a remote notification.

There are also **local notifications**, which are generated directly by the application. Those are a separate topic.

# 6. Why Include Data in a Notification?

One of the most useful features is attaching custom data to a notification.

For example:

-------------------code----------------------
{
  "listingId": 123
}
-------------------code----------------------

Then when the user taps the notification:

-------------------code----------------------

  notification.notification.request.content.data;

console.log(data.listingId);
-------------------code----------------------

We could use that ID to navigate to:

-------------------code----------------------
Listing Details
       |
       v
Listing #123
-------------------code----------------------

This is the foundation for implementing notification-based navigation.

# 7. Applying It to Your Current `AppNavigator`

Your current `AppNavigator` uses React Navigation's bottom tabs:

-------------------code----------------------
const Tab = createBottomTabNavigator();
-------------------code----------------------

We need to convert the component from an implicit return:

-------------------code----------------------
const AppNavigator = () => (
  <Tab.Navigator>
    ...
  </Tab.Navigator>
);
-------------------code----------------------

into a function body so we can register the notification listener.

For example:

-------------------code----------------------
const AppNavigator = () => {
  notifications.addNotificationResponseReceivedListener(
    (notification) => {
      console.log(notification);
    }
  );

  return (
    <Tab.Navigator>
      ...
    </Tab.Navigator>
  );
};
-------------------code----------------------

However, there is an important React consideration here: **you should not register a listener on every render**.

The better approach is to use `useEffect` and clean up the listener when the component unmounts.

---

# 8. Recommended Implementation

Import `useEffect`:

-------------------code----------------------
import React, { useEffect } from "react";
-------------------code----------------------

Then register the listener inside `useEffect`:

-------------------code----------------------
useEffect(() => {
  const subscription =
    notifications.addNotificationResponseReceivedListener(
      (notification) => {
        console.log(notification);
      }
    );

  return () => subscription.remove();
}, []);
-------------------code----------------------

### Why this is better

The empty dependency array:

-------------------code----------------------
[]
-------------------code----------------------

means the listener is registered when the component is mounted.

The cleanup:

-------------------code----------------------
return () => subscription.remove();
-------------------code----------------------

removes the listener when the component is unmounted.

This prevents multiple listeners from accidentally accumulating.

Now we want to do something useful with that event:

-------------------code----------------------

        ↓

        ↓

        ↓

-------------------code----------------------

For example, we can send the user directly to the **Account** screen, or later to a specific listing/message screen based on notification data.

---

# 2. The Problem: `AppNavigator` Has No `navigation` Prop

Normally, React Navigation gives a screen component a `navigation` prop:

-------------------code----------------------
function SomeScreen({ navigation }) {
  navigation.navigate("Account");
}
-------------------code----------------------

However, `AppNavigator` itself is the root navigator component.

It isn't registered as a screen inside another navigator, so it doesn't receive:

-------------------code----------------------
navigation
-------------------code----------------------

Therefore, this will not work:

-------------------code----------------------
const AppNavigator = ({ navigation }) => {
  // ...
};
-------------------code----------------------

---

# 3. We Also Cannot Use `useNavigation`

Another idea would be:

-------------------code----------------------
const navigation = useNavigation();
-------------------code----------------------

But the lecture explains that this also causes a runtime error in this situation.

So we need another way to access the root navigation object.

The solution is a **navigation ref**.

---

# 4. Create a Navigation Reference

Go to:

-------------------code----------------------
navigation/
-------------------code----------------------

Create a new file:

-------------------code----------------------
rootNavigation.js
-------------------code----------------------

The purpose of this file is to provide a central navigation object that can be accessed from different parts of the application.

---

# 5. Create `navigationRef`

Inside `rootNavigation.js`:

-------------------code----------------------

export default navigationRef;
-------------------code----------------------

### What does `createRef()` do?

It creates a reference object:

-------------------code----------------------
navigationRef
-------------------code----------------------

Later, React Navigation will attach the actual navigation object to:

-------------------code----------------------
navigationRef.current
-------------------code----------------------

---

# 6. Connect the Ref to `NavigationContainer`

Now go to:

-------------------code----------------------

-------------------code----------------------

Your `NavigationContainer` needs to receive the ref.

Instead of creating the ref directly inside `App.js`, import the centralized ref:

-------------------code----------------------

-------------------code----------------------

Then:

-------------------code----------------------

  ...
</NavigationContainer>

-------------------code----------------------

       |

       v
navigationRef
       |
       v
navigationRef.current
       |
       v
Navigation object
-------------------code----------------------

# 7. Create a Simple `navigate()` Function

Accessing this directly everywhere would be ugly:

-------------------code----------------------
navigationRef.current.navigate(...)
-------------------code----------------------

So we create a wrapper function.

In:

-------------------code----------------------
navigation/rootNavigation.js
-------------------code----------------------

add:

-------------------code----------------------
const navigate = (name, params) => {
  navigationRef.current?.navigate(name, params);
};
-------------------code----------------------

The parameters correspond to React Navigation's normal:

-------------------code----------------------
navigation.navigate(name, params);
-------------------code----------------------

---

# 8. Why `?.` Is Important

This:

-------------------code----------------------
navigationRef.current?.navigate(name, params);
-------------------code----------------------

uses optional chaining.

It means:

-------------------code----------------------
If navigationRef.current exists:
    call navigate()
Otherwise:
    do nothing
-------------------code----------------------

This is important because the navigation container might not have been rendered yet.

At that moment:

-------------------code----------------------
navigationRef.current
-------------------code----------------------

could still be:

-------------------code----------------------
null
-------------------code----------------------

Without optional chaining:

-------------------code----------------------
navigationRef.current.navigate(...)
-------------------code----------------------

could cause an error.

---

# 9. Export the Navigation API

Instead of exporting only the ref, we can export an object containing our navigation functions:

-------------------code----------------------
export default {
  navigate,
};
-------------------code----------------------

Now other modules don't need to know about:

-------------------code----------------------
navigationRef.current
-------------------code----------------------

They can simply use:

-------------------code----------------------
navigation.navigate("Account");
-------------------code----------------------

This gives us a cleaner abstraction.

---

Go to:

-------------------code----------------------

-------------------code----------------------

*** 10- Creating a Custom Hook ***
# Push Notifications: Extracting Notification Logic into a Custom Hook

## 1. Goal

The notification functionality works, but there is now a design problem.

`AppNavigator` contains too much **business logic**:

* Requesting notification permissions
* Getting the Expo push token
* Sending the token to the server
* Listening for notification responses
* Handling notification taps

The goal is to move this logic into a reusable custom hook:

-------------------code----------------------
hooks/
└── useNotifications.js
-------------------code----------------------

Then `AppNavigator` only needs to say:

-------------------code----------------------
useNotifications();
-------------------code----------------------

This makes the navigator much cleaner.

---

# 2. Why Move This Logic?

A UI/navigation component should mainly be responsible for:

-------------------code----------------------
Rendering UI
Navigation
Screen configuration
-------------------code----------------------

It shouldn't contain all the implementation details of push notifications.

Instead:

-------------------code----------------------
AppNavigator
     |
     v
useNotifications()
     |
     +--> Request permission
     |
     +--> Get push token
     |
     +--> Send token to server
     |
     +--> Listen for notifications
-------------------code----------------------

This is an example of **separation of concerns**.

---

# 3. Create the Custom Hook

Go to your:

-------------------code----------------------
hooks/
-------------------code----------------------

folder.

Create:

-------------------code----------------------
useNotifications.js
-------------------code----------------------

Start with:

-------------------code----------------------
import { useEffect } from "react";

export default function useNotifications() {
}
-------------------code----------------------

The `useNotifications` function will contain all notification-related logic.

---

# 4. Move the Notification Imports

The notification code previously required imports such as:

-------------------code----------------------
import * as Notifications from "expo-notifications";
import * as Permissions from "expo-permissions";
import { useEffect } from "react";
-------------------code----------------------

These belong inside the hook because the hook now owns the notification logic.

So:

-------------------code----------------------
import { useEffect } from "react";
import * as Notifications from "expo-notifications";
import * as Permissions from "expo-permissions";
-------------------code----------------------

---

# 5. Move the Expo Push Token API

Previously, `AppNavigator` imported the API responsible for registering the push token.

Move that import into the hook:

-------------------code----------------------
import expoPushTokensApi from "../api/expoPushTokens";
-------------------code----------------------

Your hook now has everything it needs to register the device.

---

# 6. Register for Push Notifications

The first part of the `useEffect` should request permission and obtain the Expo push token.

The basic flow is:

-------------------code----------------------
Ask permission
     |
     v
Permission granted?
     |
    Yes
     |
     v
Get Expo push token
     |
     v
Send token to server
-------------------code----------------------

Example:

-------------------code----------------------
const registerForPushNotifications = async () => {
  try {
    const permission = await Permissions.askAsync(
      Permissions.NOTIFICATIONS
    );

    if (!permission.granted) return;

    const token =
      await Notifications.getExpoPushTokenAsync();

    await expoPushTokensApi.register(token.data);
  } catch (error) {
    console.log(
      "Error getting a push token",
      error
    );
  }
};
-------------------code----------------------

Depending on the Expo SDK version used by your project, the exact notification/permission API may differ. Keep the API style consistent with the version already used in your project.

---

# 7. Register the Notification Listener

Previously, the listener was hard-coded inside `AppNavigator`.

The problem is that different applications might want to do different things when a notification is tapped.

For example:

-------------------code----------------------
App A:
Notification → Account screen

App B:
Notification → Listing details

App C:
Notification → Message screen
-------------------code----------------------

Therefore, the hook should not decide what happens after a notification is tapped.

Instead, it should accept a callback.

---

# 8. Add `notificationListener`

Change the hook:

-------------------code----------------------
export default function useNotifications(
  notificationListener
) {
}
-------------------code----------------------

Now the component using the hook can decide what happens.

For example:

-------------------code----------------------
useNotifications((notification) => {
  console.log(notification);
});
-------------------code----------------------

---

# 9. Only Register the Listener When Needed

The hook should check whether a listener was provided:

-------------------code----------------------
if (notificationListener) {
  const subscription =
    Notifications.addNotificationResponseReceivedListener(
      notificationListener
    );
}
-------------------code----------------------

This makes the hook reusable.

If a component doesn't need to react to notifications:

-------------------code----------------------
useNotifications();
-------------------code----------------------

No listener is registered.

---

# 10. Complete Hook Structure

The final structure is:

-------------------code----------------------
export default function useNotifications(
  notificationListener
) {
  useEffect(() => {
    // Register for notifications

    // Register notification listener

    // Cleanup listener
  }, []);
}
-------------------code----------------------

The cleanup is important:

-------------------code----------------------
return () => subscription.remove();
-------------------code----------------------

This prevents the same listener from accumulating multiple times.

# 13. Full Final Code

## `hooks/useNotifications.js`

Using the notification API style from the lecture:

-------------------code----------------------
import { useEffect } from "react";
import * as Notifications from "expo-notifications";
import * as Permissions from "expo-permissions";

import expoPushTokensApi from "../api/expoPushTokens";

export default function useNotifications(
  notificationListener
) {
  useEffect(() => {
    const registerForPushNotifications = async () => {
      try {
        const permission = await Permissions.askAsync(
          Permissions.NOTIFICATIONS
        );

        if (!permission.granted) return;

        const token =
          await Notifications.getExpoPushTokenAsync();

        await expoPushTokensApi.register(token.data);
      } catch (error) {
        console.log(
          "Error getting a push token",
          error
        );
      }
    };

    registerForPushNotifications();

    let subscription;

    if (notificationListener) {
      subscription =
        Notifications.addNotificationResponseReceivedListener(
          notificationListener
        );
    }

    return () => {
      if (subscription) {
        subscription.remove();
      }
    };
  }, [notificationListener]);
}
-------------------code----------------------

*** 11- Local Notifications ***
# Local Notifications in Expo

## 1. Remote vs. Local Notifications

Expo supports two main types of notifications:

1. **Remote notifications (Push notifications)**

   * Sent from a server through Expo's notification infrastructure.
   * Can reach the user's device even when the app isn't running.
   * This is what we implemented in the previous lessons.

2. **Local notifications**

   * Created directly inside the mobile application.
   * Do not require a server.
   * Useful for reminders, order confirmations, scheduled events, etc.
   * Can be tested using an emulator/simulator.

The important distinction is:

-------------------code----------------------
Remote:
Server → Expo → Device

Local:
App → Device
-------------------code----------------------

---

# 2. Import Expo Notifications

Just like with push notifications, import the Expo notifications API.

-------------------code----------------------
import * as Notifications from "expo-notifications";
-------------------code----------------------

---

# 3. Display a Local Notification Immediately

Suppose we have a button and want to display a notification when the user presses it.

Use:

-------------------code----------------------
Notifications.presentNotificationAsync()
-------------------code----------------------

Example:

-------------------code----------------------
const handleNotification = async () => {
  await Notifications.presentNotificationAsync({
    title: "Congratulations",
    body: "Your order was successfully placed.",
    data: {
      displayInForeground: true,
    },
  });
};
-------------------code----------------------

Then connect it to a button:

-------------------code----------------------jsx
<Button
  title="Show Notification"
  onPress={handleNotification}
/>
-------------------code----------------------

### What happens?

When the user taps the button:

-------------------code----------------------
Button pressed
     ↓
handleNotification()
     ↓
presentNotificationAsync()
     ↓
Notification appears
-------------------code----------------------

---

# 4. Show Notifications While the App Is in the Foreground

On iOS, notifications normally aren't displayed while the application is in the foreground unless configured appropriately.

The lecture initially uses:

-------------------code----------------------
data: {
  displayInForeground: true,
}
-------------------code----------------------

For example:

-------------------code----------------------
await Notifications.presentNotificationAsync({
  title: "Congratulations",
  body: "Your order was successfully placed.",
  data: {
    displayInForeground: true,
  },
});
-------------------code----------------------

However, if you need this behavior consistently, configuring it globally is preferable.

---

# 5. Configure Foreground Notifications in `app.json`

Instead of repeatedly adding:

-------------------code----------------------
data: {
  displayInForeground: true,
}
-------------------code----------------------

you can configure the behavior in `app.json`.

Example:

-------------------code----------------------
{
  "expo": {
    "notification": {
      "iosDisplayInForeground": true
    }
  }
}
-------------------code----------------------

Then your JavaScript becomes simpler:

-------------------code----------------------
await Notifications.presentNotificationAsync({
  title: "Congratulations",
  body: "Your order was successfully placed.",
});
-------------------code----------------------

### Important

The exact Expo configuration syntax can depend on the Expo SDK version you're using. The lecture uses the older Expo notification configuration style, so when working on a current project, check the Expo documentation for the configuration format appropriate to your SDK.

# 6. Schedule a Notification for the Future

Local notifications don't have to appear immediately.

Expo also provides:

-------------------code----------------------
Notifications.scheduleNotificationAsync()
-------------------code----------------------

The first argument contains the notification.

The second argument contains the schedule.

Conceptually:

-------------------code----------------------
await Notifications.scheduleNotificationAsync(
  {
    content: {
      title: "Congratulations",

      date: futureDate,
    },
  }
);
-------------------code----------------------

We can calculate a future date using JavaScript's `Date` object.

-------------------code----------------------
const date = new Date();

-------------------code----------------------

-------------------code----------------------
await Notifications.scheduleNotificationAsync({

  },

    date,

-------------------code----------------------

-------------------code----------------------

      ↓

      ↓
Add 2 seconds
      ↓
Schedule notification
      ↓
Wait 2 seconds
      ↓
Notification appears
-------------------code----------------------

---

# 8. Immediate vs. Scheduled Notifications

| Method                        | Purpose                            |
| ----------------------------- | ---------------------------------- |
| `presentNotificationAsync()`  | Show notification immediately      |
| `scheduleNotificationAsync()` | Show notification at a future time |

### Immediate

-------------------code----------------------
await Notifications.presentNotificationAsync({
  title: "Congratulations",
  body: "Your order was successfully placed.",
});
-------------------code----------------------

### Scheduled

-------------------code----------------------
await Notifications.scheduleNotificationAsync({
  content: {
    title: "Congratulations",
    body: "Your order was successfully placed.",
  },
  trigger: {
    date,
  },
});
-------------------code----------------------

---

# 9. Why Local Notifications Are Useful

Local notifications are useful when the app itself knows when something should happen.

Examples:

* Medication/reminder apps
* Calendar reminders
* Alarm applications
* Order status reminders
* Scheduled tasks
* Countdown notifications
* Offline reminders

A server is not necessary for these notifications.

---

# 10. Important Notes and Best Practices

### 10.1 Local notifications don't need a push token

Unlike remote notifications, you don't need:

-------------------code----------------------
Expo Push Token
-------------------code----------------------

because the notification is created locally.

### 10.2 Local notifications can be tested in a simulator

This is an important difference from the previous push notification implementation.

Remote push notifications generally require a physical device for testing.

Local notifications can be tested in a simulator/emulator.

### 10.3 Prefer global configuration for repeated behavior

If every notification needs the same foreground behavior, configuring it globally is cleaner than repeatedly adding the same property to every notification.

### 10.4 Use `async/await`

Notification APIs return promises, so use:

-------------------code----------------------
await Notifications.presentNotificationAsync(...)
-------------------code----------------------

or:

-------------------code----------------------
await Notifications.scheduleNotificationAsync(...)
-------------------code----------------------

This makes asynchronous behavior easier to understand.

# 11. Full Final Code

The lecture's final example demonstrates a button that schedules a local notification two seconds into the future.

A clean modern version of that example is:

        date,
      },

  };

        title="Show Notification"
        onPress={handleNotification}
      />
    </View>

-------------------code----------------------

A new API module is created:

-------------------code----------------------
